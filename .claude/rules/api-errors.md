# Validation des entrées et codes d'erreur API

Déplacé tel quel depuis CLAUDE.md (sections « lang et ageGroup », puce de validation, et « Codes d'erreur API (FailedStep) »), le 2026-10-21.

## lang et ageGroup
- **Validés à l'entrée de TOUTE route qui les lit** (`/generate/*` via `BODY_CHECKS`, chat, recherche web, upload/voice/text/detect-consigne, vocal-answer, read-aloud) : absents → défaut de la route ; présents mais invalides → **400 `invalid_input`**, AVANT tout appel IA, toute modération et toute écriture. `lang` finit tel quel dans `langInstruction` (un code inconnu n'est pas traduit) : du texte libre y serait une injection de consignes que la modération ne voit pas. Source unique `helpers/request-validation.ts` : `isLangCode` (BCP-47 simple, ancré, sans drapeau `m` : 2-3 lettres + 2 sous-étiquettes max, ex. `pt-BR`), `readLocaleFields`, `readBodyLang`, `rejectInvalidLang` ; `isAgeGroup` vit dans `profiles.ts` (`Object.hasOwn` : `constructor`/`__proto__` refusés). Upload multipart : un refus supprime les fichiers déjà écrits par multer. Jamais ces prédicats dans `routes/generate.ts` (mocké par d'autres tests).

## Codes d'erreur API (FailedStep)
- Une génération en échec porte un code stable (`types.ts` : `FailedStepCode`) : réponse des routes `/generate/<type>`, entrée du tracker, étape d'un lot Auto (`steps[].failureCode`, cf. `auto-runs.md`) — jamais `err.message` brut dans une réponse ou un événement (fuite potentielle clés API / URLs internes)
- **Source unique** : `types.ts` exporte `FailedStepCode`. Toute addition casse `helpers/error-codes.test.ts` (_KNOWN_CODES) tant que le nouveau code n'est pas listé → force une revue volontaire des consommateurs (UI mapping, retry policy, observabilité).
- Codes : `llm_invalid_json`, `quota_exceeded`, `upstream_unavailable` (503/529 panne backend, ou délai dépassé / connexion impossible levés par le SDK sans statut : `matchTransport`, évalué APRÈS les règles audio pour qu'un échec du TTS garde `tts_upstream_error`), `auth_required` (401/403 OU clé API locale non définie), `refused` (étape d'un lot Auto refusée par ses gardes, code exact du refus dans `refusal` : posé par le cœur de génération, jamais par `extractErrorCode`), `content_refused` (refus du garde-fou de Mistral : 403, `guardrail_violation`, code 1920, lu dans le message de l'erreur du SDK par `matchGuardrail`, évalué AVANT les règles de statut ; déterministe, jamais rejoué par le TTS ; relevé le 2026-10-21 sur une phrase hindie anodine, qui partait en `auth_required` avec un message de clé API), `tts_upstream_error`, `context_length_exceeded`, `internal_error`
- **Tous les endpoints** qui renvoient une erreur HTTP doivent utiliser `extractErrorCode(e, '<agent>')` plutôt que `err.message`/`String(e)` (cf. `helpers/error-codes.ts`) — ne pas en créer de nouveaux sans cette pratique.
- **Limiteurs** (`helpers/rate-limit.ts`) : tout 429 répond `{ error: 'rate_limited' }` (jamais de texte libre) avec `Retry-After` (secondes) ; front : `resolveError` / `mapServerErrorCode` → `errorCode.rate_limited`, refus d'un PIN → `profile.pinRateLimited` avec les minutes lues dans `Retry-After` (15 par défaut). `generalLimiter` (300/min) monté AVANT la première route `/api` (les routes de config lui échappaient) ; `aiLimiter` (60/min) monté UNE fois par `aiPathLimiter` (`AI_PATH_RE` : generate, sources, chat, detect-consigne, moderate, `generations/:gid/(vocal-answer|read-aloud)` ; drapeau `i` et barre finale tolérée, le routage d'Express 5 ignorant la casse — mesuré), avant la clé et multer — **jamais de `router.use(aiLimiter)`** dans un routeur (il comptait deux fois le chat et limitait tentatives, renommage, suppression et annulation) ; `authLimiter` (30 / 15 min) sur la seule création de profil ; `pinLimiter` (10 PIN faux / 15 min par IP) sur `PUT`/`DELETE /api/profiles/:id` : sans `pin` ni comptée ni bloquée, seuls les 403 restent comptés, au-delà 429 même pour le bon PIN. Compteurs en mémoire (un redémarrage les remet à zéro). Verrou : `helpers/rate-limit.test.ts` (vraies apps Express, port éphémère).
- **Recherche web** (`POST /:pid/sources/websearch`, `routes/sources.ts`) : au moins une source créée → 200 inchangé (array nu, ou `{ sources, failures }`) ; aucune → **422** `{ error: 'url_blocked', failures }` si la garde SSRF a rejeté TOUTES les tentatives, sinon **502** `{ error: 'all_sources_failed', failures }` (repli en échec, erreur de l'API, mélange avec des rejets SSRF), cf. `respondNoWebSources`. `failures[] = { label, code }` : `url_blocked` pour un rejet SSRF (journalisé en `warn` sans stack), sinon `extractErrorCode` de l'erreur, que le repli `fallbackWebSearchUrl` propage (il ne l'avale plus en `null` : `quota_exceeded`, `auth_required`… arrivent au front). Front : `websearchErrorCode` (`src/app/websearch.ts`) affiche le code que partagent tous les échecs s'il est parlant (≠ `internal_error`), sinon le code global, traduit par `resolveError`.
- **Corps JSON refusés par body-parser** (`server.ts`, juste après `express.json`) : JSON malformé → 400 `invalid_json` ; corps trop gros (> 5 Mo) → 413 `payload_too_large` ; autre refus exposé (jeu de caractères ou encodage inconnu en 415, corps compressé illisible en 400) → son statut + `invalid_json`. Avant le 2026-10-24, ces refus partaient dans le handler HTML d'Express.
- **Uploads multipart** : tout middleware multer DOIT être enveloppé par `withUploadErrors` (`helpers/upload-errors.ts`) → `file_too_large` (413), `upload_failed` (400 : multipart invalide ou garde-fou), `internal_error` (500 : panne du stockage). Sans lui, une erreur multer part dans le handler Express par défaut (500 + page HTML avec stack hors production) et l'UI affiche « Internal Server Error ». Verrou : `routes/upload-guards.test.ts`.
- Le détail complet (stack, message) reste dans `logger.error` côté serveur
- **Traduction** : tout code stable renvoyé (`{ error: 'code' }`) a sa clé `errorCode.<code>` dans les 9 langues (verrou : `src/i18n/i18n-sync.test.ts`, qui lit les sources du serveur : `error: '…'`, constantes `ERR_*` et `ValidationError(4xx, '…')`). **Jamais de texte dans un refus** (même verrou) : « Projet introuvable », « Nom requis »… s'affichaient en français dans les 9 langues. Requête mal formée → `invalid_input` (`INVALID_INPUT`, `helpers/request-validation.ts`), la raison précise part dans les journaux (`logger.warn`, profils) ; ressource absente → `project_not_found`, `generation_not_found`, `source_not_found`, `profile_not_found` ; PIN faux → `pin_wrong` ; enregistrement vocal sans parole → `empty_transcription`. Front : `resolveError` et `mapServerErrorCode` traduisent tout code qui a sa clé, sans liste blanche (celle de `mapServerErrorCode` laissait `stale` s'afficher brut).
- **Architecture interne** : `helpers/error-codes.ts` est un re-export mince. La logique vit dans `helpers/error-code-resolution.ts` (orchestration), `helpers/error-code-rules.ts` (règles par agent), `helpers/error-matchers.ts` (matchers par pattern d'erreur — chaque matcher délimité `export function` pour contourner le parseur Lizard TS qui agglomère sinon les `function foo()` top-level consécutives).
- **Statut HTTP d'une erreur = `httpStatusOf(err)`** (`helpers/error-code-resolution.ts`) : `statusCode` (les erreurs HTTP du SDK Mistral n'ont **jamais** `status`), sinon `status`. Lire `status` seul rendait `STATUS_RULES` et le réessai applicatif inertes jusqu'en v1.7.3 : seul le message (« Status 503 … ») était analysé, et un corps qui parle de « rate limit » faisait d'un 503 un `quota_exceeded`. **Deux couches de réessai, jamais sur le même code** : le SDK rejoue ses `retryCodes` (429, 500, 502, 503, 504, sur toutes ses opérations) avec le backoff de `RETRY_CONFIG` (nouvelles tentatives pendant 120 s, chacune bornée à 120 s depuis le SDK 3 : ≈ 250 s au pire par appel) ; `callWithRetry` (`helpers/mistral-retry.ts`) ne rejoue QUE ce qu'il ignore (408, autres 5xx dont 520-529 de Cloudflare, placé devant l'API) + le bug de clonage du SDK. Rejouer les deux fois multiplierait l'attente (jusqu'à ~6 min sur un 429 persistant). Source : `SDK_RETRIED_STATUSES` ; verrou au bump du SDK : `mistral-client-factory.contract.test.ts`. **Bug de clonage** (mesuré le 2026-10-03, SDK 2.7.0, Node 22.18) : quand l'API répond 429 ou 503 avant d'avoir reçu tout le corps de la requête (HTTPS, gros corps : une rafale de générations), le réessai du SDK échoue sur `request.clone()` d'undici (`TypeError: unusable`), et le SDK enveloppe ce TypeError dans un `UnexpectedClientError` (`cause`) → `isSdkCloneBug` lit l'erreur ET sa cause, et `callWithRetry` reprend avec une requête neuve. Ne lire que `instanceof TypeError` laissait passer toutes les vraies erreurs (18 quiz en `internal_error` d'affilée, 0 réessai). Tests : de vraies erreurs du SDK (`SDKError`, `UnexpectedClientError` de `@mistralai/mistralai/models/errors`), jamais des `{ status }` ou un `TypeError` nu fabriqués à la main (ils validaient une branche que les vraies erreurs n'atteignaient pas).

# Générations en cours et notifications

Déplacé tel quel depuis CLAUDE.md (section « Pending generations & notifications »), le 2026-10-21.

## Pending generations & notifications

Cycle de vie des générations en cours :

- **Refresh / switch profil ≠ cancel**. Invariant absolu : la fermeture du socket HTTP côté client (refresh, switch onglet, switch profil, navigation, perte réseau) **ne déclenche AUCUN cancel serveur**. La génération continue, persiste son résultat en `completed` même si `res.json()` part dans le vide. Le seul chemin d'annulation = `POST /api/projects/:pid/generations/:gid/cancel` explicite. Ne JAMAIS brancher `req.on('close')` pour annuler une génération.
- **N générations du même type en parallèle** : re-cliquer un bouton lance une génération de plus (`canStartGenerate` ne verrouille PAS sur `loading[type]`). `loading[type]` **reste booléen** ; il n'est libéré (cleanups single/all/auto + cancel) que s'il ne reste AUCUN autre pending du type via la fonction pure **`pendingOfTypeExists(pendingById, type)`** (`src/app/pending-utils.ts` — module dédié pour rester hors du `vi.mock('./helpers')` des tests ; param `| undefined` pour tolérer un state partiel). Les boutons des 9 vues sont **statiques cliquables** (pas de `isLoading` sur leur `:disabled`) ; les N pendings restent visibles/annulables via les chips (1 par gid). Pas de debounce (il bloquait des retries légitimes).
- **Côté serveur, même projet + même type = l'un après l'autre** (`withSameTypeQueue`, `routes/generate.ts` : `withKeyedLock` sur `generate:<pid>:<type>`, types à bloc d'exclusions seulement, `hasExclusionContext` ; génération simple ET étapes du mode Auto). Le bloc d'exclusions est lu au lancement : deux générations simultanées ne s'y voyaient pas et commençaient par le même élément (vécu le 2026-10-05 : deux textes à trous lancés à 0,4 s d'écart ; mesuré le 2026-10-07, `output/parallele-corpus/`, hors git : même 1er élément 2 à 7 fois sur 8 en parallèle). À son tour, la génération relit le projet (exclusions à jour) ; annulée pendant son attente (`store.pendingStatus`), elle répond 409 `cancelled` sans appeler Mistral. Types différents : toujours en parallèle (quiz + flashcards ensemble : 18 s, deux quiz : 32 s). L'anti-flood compte toujours les générations en file.
- **Quiz et textes à trous : quelques éléments de plus, les inédits d'abord** (`generateFresh`, `EXTRA_WHEN_PREVIOUS` : 10 questions de quiz, 5 textes à trous) quand des séries du même type existent : même l'un après l'autre, le bloc ne suffisait pas (textes à trous : le terme central de la leçon revenait en tête ; quiz avec consigne : les mêmes questions sur ses points, recouvrement 0,76). `preferUnusedAnswers` (`answerKey` : casse, accents, apostrophe, article ignorés) et `preferUnseenQuestions` (60 % de mots communs) les font passer après les inédits, puis coupe au nombre demandé → 0 fois sur 8 le même 1er élément. Détail et en-tête du quiz : `.claude/rules/prompts.md` (Bloc d'exclusions).
- **Anti-flood : au plus `MAX_PARALLEL_PER_TYPE` = 3 générations du même type en cours** (`src/app/pending-utils.ts`, vécu le 2026-10-03 : ~18 appuis en 3 s d'une enfant sur « Quiz » → 18 générations, refusées en partie par Mistral, 18 toasts d'erreur). Plafond par NOMBRE, jamais par délai (double-clic = 2 générations, réessai après échec possible : une génération échouée ne compte plus). Compté dans `runSingleGenerate` (`src/app/generate.ts` : clics des vues, version facile à lire, « Réessayer ») = `countPendingOfType(pendingById, type)` (cet onglet + autres onglets/appareils du projet via SSE) + **réservations** `launchingByType[type]` ; au-delà → toast **info** `toast.generationBusy`, rien n'est lancé. Piège : le pré-contrôle de modération (`checkGenerationAllowed`, jusqu'à 8 s) passe AVANT le pending optimiste → la réservation est prise de façon SYNCHRONE au clic (`reserveLaunch`), gardée pendant l'attente, et rendue (`releaseLaunch`) dans le même bloc synchrone que la création du pending (aucun appui ne s'intercale) ou sur un refus ; `resetSession` vide la map (jamais de compteur négatif). Sans la réservation, tous les appuis d'une rafale passaient (verrou : tests « rafale » de `generate.test.ts`, qui échouent sans elle). Hors champ : Auto (bouton désactivé par `isGenerating()` ; un seul Auto en cours par cours, registre `autoRuns`), remédiation (`reviewing`), chat (`chatLoading`), API (aucun plafond serveur).
- **gid généré côté client** (`crypto.randomUUID()` dans `src/app/generate.ts`), passé au backend via `body.gid`. Permet `abortControllersByGid[gid]` immédiat et identifiant stable utilisable au moment du payload 200 fallback ou de l'event SSE. Le backend valide UUID v4 STRICT (`readClientGid` dans `routes/generate.ts` — version nibble = `4`, variant nibble dans `[89ab]`, aligné sur la regex client `confirm.ts:GID_UUID_V4`) ou retombe sur `randomUUID()` en cas de gid invalide. Les étapes d'un lot Auto reçoivent chacune un gid serveur (`startAutoRunSteps`, cf. `auto-runs.md`).
- **Race promote/cancel** : `store.promoteToGeneration` retourne `PromoteResult = { kind: 'promoted', generation } | { kind: 'cancelled' } | { kind: 'failed', code } | { kind: 'missing' }`. Le handler dispatche : `200 generation` si promoted, `409 PromoteErrorResponse` (`types.ts`, `PromoteErrorOutcome = 'cancelled' | 'failed'` — pas `'missing'`) sinon. **Le `kind: 'missing'` du store est remappé server-side vers `error: 'failed'` côté wire** (source unique `classifyPromoteFailure` dans `routes/generate.ts`) car `'missing'` = symptôme bug observabilité (entry retirée du tracker entre cancel et promote), surfaceable seulement par `logger.error` (Sentry), jamais comme code applicatif côté client. Le type HTTP est découplé du discriminant store pour qu'un futur rename de `kind` ne casse pas le client. Plus de réponse 200 fantôme quand un cancel arrive pendant que Mistral travaille.
- **Boot sweep** : `store.cancelAllPendingsAtBoot()` au démarrage marque tous les `pendingTracker[].status === 'pending'` comme `cancelled`. Pas de TTL — par construction, tout pending sur disque vient d'un process mort. Si `getProject(meta.id)` retourne null (project.json corrompu), `logger.error` dédié (niveau **error volontaire** : project.json corrompu = bug observabilité critique, pas un warn) pour signaler les pendings ghost laissés en place. Le tracker est aussi pruné à chaque save : `pruneTrackerIfNeeded` applique en permanence l'intersection **max 50 terminaux ET ≤ 7 jours d'âge** (un terminal gardé doit satisfaire les deux contraintes ; les pendings actifs ne sont jamais prunés). Appelé sur **chaque save**, pas seulement quand `length > 50`, sinon des terminaux > 7j s'accumulent silencieusement sous le seuil.
- **`pendingTracker` séparé de `generations[]`** dans `ProjectData.results` (`types.ts`). Évite de polluer `generations: Generation[]` avec des entrées sans `data`. Promotion = remove du tracker + push dans generations atomique dans le même `saveProject`. Les terminaux ne suivent pas ce chemin : `markPendingFailed`/`markPendingCancelled` (et le helper privé `replacePendingWithTerminal`) remplacent l'entrée par index avec l'arm terminale et la gardent jusqu'au pruning.
- **`PendingTrackerEntry` est une discriminated union sur `status`** (`types.ts`) : `PendingTrackerEntryActive` (status: 'pending') | `PendingTrackerEntryTerminal` (status: 'failed' | 'cancelled', `failureCode` + `completedAt` OBLIGATOIRES). Conséquence : `markPendingFailed`/`markPendingCancelled`/`cancelAllPendingsAtBoot` ne peuvent PAS muter `entry.status` in-place — ils construisent un nouvel objet terminal et remplacent par index dans le tracker (cf. `replacePendingWithTerminal`). Ferme à compile-time l'état impossible `{status: 'pending', failureCode: 'cancelled'}`.
- **SSE format obligatoire** sur `GET /api/projects/:pid/events` : `event: generation\ndata: {...}\n\n`. La ligne `event:` est obligatoire pour matcher `addEventListener('generation', ...)` côté client. Sans elle, l'event tombe sur le canal `'message'` générique. Heartbeat `: keep-alive\n\n` toutes les 25s, avec compteur `HEARTBEAT_MAX_CONSECUTIVE_THROWS=3` pour cleanup forcé si `req.on('close')` ne fire jamais (bug Node socket half-open). Le payload SSE est typé `GenerationEvent` (`types.ts`), discriminated union sur `status` partagée serveur ↔ client : `generation` n'existe que sur `'completed'`, `failureCode` que sur `'failed'`/`'cancelled'`. Même flux, ligne `event: auto` : état complet d'un lot Auto (`AutoRunEvent`, cf. `auto-runs.md`).
- **Idempotence à 2 niveaux côté client** :
  - `appendNotification(profileId, {eventKey, ...})` dans `src/app/notifications.ts` est idempotent par `eventKey` via le ledger localStorage `sf-profile-seen-events` (LRU cap 1000/profil, **JAMAIS cleared** — sinon réconciliation recrée les notifs supprimées). LRU régression-lockée dans `notifications.test.ts` (push 1001 → 1er évincé).
  - `shownToastEventKeys: Set<EventKey>` (type branded importé depuis `helpers/event-bus`) dans le state Alpine est la dédup tab-locale du toast UI. Un même eventKey produit max 1 toast UI par onglet.
  - Combinés : payload 200 + event SSE `completed` dans le même onglet → 1 toast et 1 notif persistée. SSE dans 2 onglets → 2 toasts (UX cohérente où l'user regarde) + 1 notif persistée cross-tabs.
  - **Génération reçue par le seul SSE** (autre onglet, étape d'un Auto du serveur ; depuis le 2026-10-28) : `applyCompletedEvent` fait comme `registerGeneration` (fiche normalisée, `initGenProps`, coût, toast avec « Voir »). **Coût compté une fois** dans l'onglet, à l'insertion (`upsertGenerationById` rend vrai pour une génération nouvelle), quel que soit l'ordre de la réponse 200 et de l'événement. `NotifSpec.projectId` range une notification sous un autre cours que celui affiché (Auto qui se termine ailleurs).
- **Toasts identiques regroupés** (`src/app/toast.ts`, vécu le 2026-10-03 : 18 échecs d'une rafale de quiz empilaient 18 toasts « Réessayer », jamais fermés, sur tout l'écran d'un téléphone) : après la dédup par `eventKey` (inchangée, la cloche garde une entrée par événement), un toast de même `type` ET même `message` déjà affiché n'est pas dupliqué → `count++` (badge `×N` + texte `sr-only`), dernier `retryFn`/`action` non nuls gardés (« Réessayer » relance UNE fois puis ferme le groupe), échéance repoussée. Fermeture automatique par **échéance** (`expiresAt`, null = persistant : erreur + réessai) relue par le minuteur, jamais par un `setTimeout` qui ferme un id : `resetSession` remet `toastCounter` à 0 et un vieux minuteur fermait un nouveau toast au même id. Échec d'une génération simple nommé par son type (`toast.typedError`, « Quiz : … ») : deux types en échec restent deux toasts, chacun avec son réessai. Signature de `showToast` : types de paramètres en alias (`ToastRetry`, `ToastActionSpec`), sinon Lizard ne mesure que la signature.
- **Notifications i18n-aware** : `PersistedNotification` porte `messageKey` + `params` + `paramKeys` (sous-clés à traduire au render — ex: `{ type: 'gen.summary' }`), traduit via `renderNotificationMessage(t)` au moment du `x-text` dans le panneau cloche. La même notif persistée donne une sortie différente selon la langue UI courante. Champ `message: string` legacy conservé en fallback pour les notifs créées avant le refactor i18n.
- **Watermark conservateur lastSeenAt** : `reconcileStartedAt = new Date().toISOString()` capturé AVANT le fetch snapshot. Cutoff de réconciliation = `Date.parse(lastSeenIso ?? reconcileStartedAt)`. Au 1er load après migration, `lastSeenAt` est absent → cutoff = now → zéro backfill historique (pas de spam de 200 notifs sur un projet existant). Set du watermark se fait avec `reconcileStartedAt` (pas `now` post-backfill) pour ne jamais masquer un event arrivé entre snapshot et ouverture SSE.
- **`resetSession()`** (`src/app/session.ts`) invoqué par `selectProfile`, `selectProject`, `deleteProject`. Stop EventSource SSE, arrête l'enregistrement vocal en cours (envoyé vers son cours, cf. ci-dessous), abort les `abortControllers` + `abortControllersByGid` SAUF ceux d'un Auto en cours (`autoRuns`), vide `loading{}`, `pendingById`, `toasts[]`, `shownToastEventKeys`, remet `chatLoading` et `consigneLoading` à false, abandonne l'ouverture d'un cours encore en cours (`projectLoadController` aborté, `projectLoading` à false, cf. ci-dessous), reset `confirmCallback` + `confirmTrigger`. **NE TOUCHE PAS** au ledger `seenEventKeys` ni à la liste `notifications` (mémoire persistante du profil, replay au retour), ni aux registres `autoRuns`, `chatInFlight` et `uploadSessions`. Régression-lockée par les tests négatifs `src/app/session.test.ts`.
- **Ce qui continue quand on change de cours ou de profil** (règle du propriétaire, 2026-10-21 : « on lance un truc, ça continue même si on change de page, sauf si techniquement on ne peut rien y faire »). Motif commun (`sources.ts` pour l'import) : l'action CONTINUE vers son cours d'origine ; son résultat ne s'applique à l'écran (sources, sélection, coût, générations, chargement, puces, toasts, messages) que si ce cours est AFFICHÉ (`currentProjectId === cours d'origine`) ; le serveur a déjà tout persisté, relu au retour (et les notifications par `reconcilePendings`). Ce qui part d'un clic et attend capture **au clic** : cours (et son nom pour un toast de fin), corps (sélection COPIÉE, consigne, nombre, langue, âge) et clé (`captureAiKey`, cf. `api-key.md`) — jamais relus à l'envoi, ils seraient ceux du cours ou du profil affichés.
  - **Auto** (`generate.ts`, `auto-runs.ts`) : registre `autoRuns[projectId] = { controller, analysing }` (state, ni `resetSession` ni `resetState` n'y touchent) ; `resetSession` épargne ce contrôleur (analyse ET étapes, même posé dans `abortControllers[type]`) ; seules l'annulation explicite (puce « Auto — analyse… » = `cancelOne('auto')`, « Tout annuler ») et la suppression du cours (`abortAutoRun` dans `deleteProject`) l'arrêtent. « Tout annuler » (`cancelGeneration`) passe aussi par `abortAutoRun` du cours affiché, dans toutes ses phases : revenu sur le cours pendant les étapes, le contrôleur n'est plus dans `abortControllers`, et ses étapes encore en file partaient après l'annulation (recette du 2026-10-21 : un texte à trous généré et facturé). Au retour sur le cours pendant l'analyse, `applyProjectSnapshot` rétablit la puce (`restoreAutoAnalysis` : `loading.auto` + `abortControllers.auto`) ; un nouveau clic Auto sur un cours qui a déjà un Auto est sans effet. Hors écran : étape réussie comptée mais ni `registerGeneration` ni toast d'étape (`showToast(…, eventKey)` écrirait la notification sous le profil et le cours AFFICHÉS), coût du routage non ajouté, `finally` gardés par cours ; fin = toast qui nomme le cours (`toast.autoDoneIn` / `autoPartialIn` / `autoFailedIn`, sans « Réessayer » : il relancerait l'Auto du cours affiché). Rien après une annulation, sur le cours affiché comme ailleurs (`showAutoOutcome` sort si le contrôleur est aborté) : « Magie terminée ! » suivait « Génération annulée » sur le cours affiché, les étapes abortées ne comptant pas comme des échecs (release-test du 2026-10-22). Jusqu'en v1.7.11, l'analyse était abortée à la navigation (facturée, aucune étape) et les étapes d'un Auto quitté n'étaient pas comptées. Ses étapes passent par la limite GLOBALE des requêtes longues (puce suivante).
  - **Requêtes longues : au plus 3 en même temps pour tout l'onglet** (`MAX_LONG_REQUESTS`, `withLongRequestSlot`, `src/app/request-slots.ts`, file au niveau du module, ni `resetSession` ni le state Alpine n'y touchent) : étapes de TOUS les Auto, générations simples (`runSingleGenerate`, envoi en arrière-plan compris) et remédiation (`quiz.ts`, réessais compris). Une seule file FIFO, la suivante part dès qu'une place se libère ; place transmise de main en main (une demande qui arrive au moment où une place se libère passe après la file, jamais une 4e place) ; place TOUJOURS rendue (`finally` : succès, erreur HTTP, exception, abort) ; attente annulable par l'`AbortSignal` de la requête (sortie de la file sans envoi, rejet `AbortError` comme un fetch aborté). Raison : le serveur parle HTTP/1.1, le navigateur n'ouvre que 6 connexions par hôte et le flux SSE en garde une ; SSE + 3 = 4, il en reste 2 pour la navigation et les appels courts. Mesures du 2026-10-21 : les 8 étapes d'un Auto lancées ensemble faisaient attendre le `GET /api/projects/:pid` d'un autre cours 10 à 15 s (release-test, `PerformanceResourceTiming`) ; la limite de 4 étapes PAR Auto qui a suivi (`MAX_PARALLEL_AUTO_STEPS`, retirée) ne suffisait pas : deux Auto (deux cours) → 8 requêtes longues + le SSE, et le bloc « Chargement... » de chaque cours ouvert restait affiché très longtemps (instance du propriétaire).
    - Auto : `MAX_LONG_REQUESTS` voies par Auto (`runAutoSteps` / `runAutoStepLane`), chaque étape attend sa place (`runAutoStep`) : seul, un Auto prend les 3 places ; avec d'autres requêtes longues, il n'a jamais plus de 3 étapes en vol ou en file et les autres passent entre ses étapes (deux Auto avancent ensemble, une génération simple n'attend pas la fin de tout un Auto) ; ordre du plan respecté ; annulé, ses étapes en file sortent de la file sans partir (`'aborted'`, ni échec ni code).
    - Génération simple : pending optimiste (puce, `loading`) dès le clic, pendant l'attente. Annulée par sa puce ou « Tout annuler » (cours affiché) → rien n'est envoyé, le `POST /cancel` reçoit un 404 (accepté). Cours ou profil quitté pendant l'attente (`resetSession` aborte aussi son contrôleur ; `selectProject`, `selectProfile` et `deleteProject` changent `currentProjectId` dans le même bloc synchrone, et le `catch` qui tranche s'exécute après : ne jamais placer ce changement après un `await`) → jamais partie, elle repart en arrière-plan (`sendGenerateInBackground` : fin de file, clé et corps du clic). Déjà partie (`SingleFlight.sent`) → pas renvoyée ; depuis le 2026-10-24 son fetch CONTINUE (registre `singleRuns`, `src/app/single-runs.ts`, épargné par `resetSession` comme `autoRuns`) et garde sa place parmi les requêtes longues jusqu'à la réponse ; au retour sur le cours, `restoreSingleRuns` (dans `applyProjectSnapshot`) remet ses contrôleurs dans `abortControllersByGid` pour que la puce ✕ et « Tout annuler » l'abortent (sinon la réponse 409 `cancelled` s'afficherait en erreur) ; suppression du cours et « Tout annuler » l'abortent aussi (`abortSingleRuns`). **Réponse arrivée pendant qu'un autre cours est affiché** (`notifySingleElsewhere`, depuis le 2026-10-24) : un toast nomme son cours (`toast.generationDoneIn`, ou `toast.generationFailedIn` avec l'erreur traduite), comme l'Auto et l'import ; rien si l'on est revenu sur le cours (le SSE prend le relais), si le profil a changé, ni après une annulation (409 `cancelled`, autre onglet). Ce toast part **sans eventKey** : avec une clé, `showToast` enregistrerait la notification sous le cours AFFICHÉ, et celle que la réconciliation pose au retour (`backfillCompletedNotifs`) serait dédoublonnée sous ce mauvais cours.
    - Hors limite : l'ouverture d'un cours, le flux SSE et les appels courts (vérification de modération, annulation) ; aussi l'analyse de route d'un Auto, le chat, la lecture à voix haute, l'import et la recherche web (une requête par action, non limitées à ce jour), et `generateAll` (aucun gabarit ne l'appelle).
  - **Ouverture d'un cours** (`selectProject`, `projects.ts`) : dès le clic, `currentProject` à null (le bloc du cours, `x-if="currentProjectId && currentProject"`, ne montre plus rien de l'ancien) et `projectLoading` à true : bloc « Chargement… » avec le nom du cours CHOISI (`currentProjectName()` : snapshot, sinon la liste `projects`), aussi dans l'en-tête et le titre du tableau de bord, au lieu de l'ancien nom et de l'état vide « Ajoute tes premières sources » (vécu au release-test du 2026-10-21, 10 à 15 s). Seule l'ouverture la plus récente s'applique (`projectLoadController`, comparé par identité) : celle qu'un autre cours, un autre profil ou la suppression du cours supplante est abortée par `resetSession` (sa requête quitte la file du navigateur) et sa réponse ignorée, sans toast ; re-toucher le cours pendant son ouverture ne relance rien. `projectLoading` repasse à false à la fin (snapshot appliqué ou échec : toast `toast.projectLoadError`, retour à la liste). Le délai lui-même reste possible si d'autres requêtes occupent les connexions.
  - **Pré-contrôle** (`checkGenerationAllowed`, `moderation-gate.ts`) : issue `allowed` | `refused` | `moved` ; cours changé pendant la vérification (`moved`) → génération simple (`sendGenerateInBackground` : sans pending, chargement ni toast), Auto (continue, toast de fin) et remédiation envoyées quand même vers le cours d'origine, le serveur refait la garde. `ensureGenerationAllowed` reste booléen (« Tout générer »).
  - **Enregistrement vocal** (`recorder.ts`) : destination capturée au DÉBUT (`VoiceTarget` : cours, nom, clé, langue) ; cours ou profil changé pendant la demande d'accès au micro → rien n'est enregistré ; `resetSession` l'arrête et `onstop` l'envoie vers son cours (jamais la voix d'un enfant dans le cours d'un autre profil, jamais d'enregistrement qui survit au changement) ; hors écran → toast `toast.voiceAddedIn` / `toast.voiceErrorIn`, rien dans les sources ni le coût affichés.
  - **Gardes de réponse** (rien à l'écran si le cours a changé, aucun toast) : recherche web, chat (ni réponse, ni générations, ni coût, ni bulle retirée sur un refus ; `chatLoading` libéré sur son cours seulement, et rétabli au retour sur ce cours tant que sa requête est en vol : registre `chatInFlight`, `chat-in-flight.ts`, relu par `applyProjectSnapshot` via `restoreChatLoading`), remédiation, lecture à voix haute d'une fiche (réponse appliquée à la génération du cours affiché qui porte le même id, objet neuf après un retour ; `readAloudInFlight` : un 2e clic après un retour ne relance pas la lecture), `refreshConsigne`, `detectConsigne` (`consigneLoading` libéré sur son cours), restauration d'un pending après un échec de `POST /cancel`.
  - Verrous : `generate.test.ts` (« generateAuto — continue vers son cours… », « requêtes longues : au plus 3 en même temps pour tout l'onglet », « projet changé pendant la vérification », « generateVoice — cours changé » ; après chaque test, aucune place des requêtes longues ne reste prise ni en file), `request-slots.test.ts`, `session.test.ts`, `recorder.test.ts`, `websearch.test.ts`, `chat.test.ts` (« retour sur le cours avant la réponse du tuteur »), `consigne.test.ts`, `confirm.test.ts` (« arrête l'Auto du cours affiché, même absent de abortControllers… »), `projects.test.ts` (« ouverture d'un cours », dont « les 3 places des requêtes longues prises… : le GET du cours part tout de suite »), `index.test.ts` (« gabarits — ouverture d'un cours »), `quiz.test.ts` (« cours changé », « places des requêtes longues toutes prises »).
- **Cœur commun des générations suivies** (`runTrackedGeneration`, `routes/generate.ts`, depuis le 2026-10-28) : reprise des modérations, gardes, entrée du tracker, file par type, générateur, coût et promotion, sans réponse HTTP ; il rend une issue (`GenerationOutcome` : `refused`, `duplicate_gid`, `promoted`, `not_promoted`, `failed`) que `handleGeneration` traduit (`sendGenerationOutcome`). Les 8 types viennent de `buildGenerationDefs` (générateur, modèle de la limite de contexte, options), un `Record` sur `AutoAgentType` : un type sans définition casse la compilation.
- **Validations early extraites des generators** (`routes/generate.ts`) : tout `return null + res.status(4xx)` doit être SORTI en pre-handler AVANT `addPendingEntry`. Sinon un input invalide laisse un pending tracker entry orphelin. Helper `validateQuizReviewInputs` montre le pattern.
- **`storage` event cross-tab** : `src/main.ts` appelle `installCrossTabSync(globalThis, document)` (cf. `src/app/cross-tab-sync.ts`) qui enregistre le `addEventListener('storage', ...)` et bumpe `state.notificationsVersion` quand `sf-profile-notifications` change dans un autre onglet. Le storage event ne fire pas dans le tab qui écrit, donc combiné avec le bump local sur `appendNotification`, tous les onglets convergent. Le helper externalisé permet le test unitaire avec un `globalThis` stubbé.
- **`sf-lastProjectId` namespacé par profil** : map `sf-profile-last-project: {profileId: projectId}` (cf. `src/app/projects.ts` helpers en arrow). Migration silencieuse one-time au boot de la clé legacy `sf-lastProjectId`. Idempotent.
- **Limite documentée Mistral SDK** : la requête en cours côté serveur n'est PAS interruptible. Le cancel ne stoppe pas la facturation, il signifie "on ignore la réponse quand elle arrive" (via `promoteToGeneration` qui retourne `cancelled` et le handler 409).
- **SSE handler garde 404 + write-after-close protection** : `GET /api/projects/:pid/events` vérifie l'existence du projet AVANT `flushHeaders` (sinon listener `EventEmitter` orphelin sur pid bidon, cap 50 → MaxListenersWarning au bout de quelques typos client). `writeGenerationEvent` wrappe les `res.write` dans try/catch + `res.writableEnded` guard (race entre dispatch event-bus et `req.on('close')` → `ERR_STREAM_WRITE_AFTER_END` propagé au listener crashait le process). `res.on('error', ...)` attaché pour cleanup sur reset TCP brutal.
- **Cancel UI optimiste avec rollback** (`src/app/confirm.ts`) : `cancelPendingByGid` retire `pendingById[gid]` immédiatement (feedback instantané), mais si `POST /cancel` échoue (réseau down / 5xx) le snapshot est restauré + toast `cancelFailed`. Sans rollback, l'user croyait que c'était annulé alors que le backend continuait. `postCancel` retourne `boolean` (true si 200 ou 404 = race acceptée, false sinon). Le toast immédiat ajoute l'eventKey `cancelled` du gid à `shownToastEventKeys` : l'événement SSE du même gid n'affiche pas un second toast identique, mais écrit toujours la notification persistée. « Tout annuler » (`cancelGeneration`) annule chaque génération par `cancelPendingSilently` (même annulation, eventKey compris, sans toast) et n'affiche qu'un toast en tout, `toast.cancelledGeneration` : un toast par génération en empilait cinq d'un coup (release-test du 2026-10-22). La puce ✕ passe par `cancelPendingByGid`, qui nomme le type.
- **`runAutoStep` propage le `errorCode` parsé** dans le tuple retourné (`{kind: 'failed', code}`) — `showAutoResult` priorise un toast actionnable (auth_required → settings, quota_exceeded → wait) sur le `partialGenerated` générique.
- **EventSource cap retries** (`src/app/sse-pendings.ts`) : après `RECONNECT_MAX_RETRIES = 8` échecs consécutifs (typiquement projet supprimé dans un autre tab → 404 répété, ou réseau durablement down), on stop la boucle de reconnect au lieu de marteler en backoff exp ad vitam. `console.warn` à chaque retry pour visibilité debug. Un `selectProject`/refresh ultérieur relance avec compteurs réinitialisés.
- **Bus filet anti-uncaughtException** (`helpers/event-bus.ts`) : `subscribeGeneration` wrappe le handler client dans try/catch + `bus.on('error', ...)` global. Sans ce filet, un throw d'un handler SSE (ex: `JSON.stringify` cyclique sur un payload buggué, write-after-end non capturé) remonte en `uncaughtException` et tue le process.

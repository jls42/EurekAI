## Modération (Moderation 2, fail-closed)
- **Source unique** : `helpers/moderation-model.ts` — `MODERATION_MODEL = 'mistral-moderation-2603'` (id daté épinglé, jamais `-latest`) + sa **taxonomie** `MODERATION_MODEL_CATEGORIES` (11 clés : `sexual`, `hate_and_discrimination`, `violence_and_threats`, `dangerous`, `criminal`, `selfharm`, `health`, `financial`, `law`, `pii`, `jailbreaking`) + table legacy 2411 → 2603 (`dangerous_and_criminal_content` → `dangerous` + `criminal`). `profiles.ts` réexporte `ALL_MODERATION_CATEGORIES`. **Bump du modèle** : suivre la procédure en tête du fichier (recapturer une réponse réelle, aligner taxonomie, table legacy, i18n `moderation.cat.*` ×9, test de contrat de `generators/moderation.test.ts`) — un bump sans cette étape a rendu la case « Contenu dangereux » inopérante (v1.5.4 → v1.7.1).
- **Migration des profils** (`migrateModerationCategories`, au chargement) : absent ou vide (`null`, `0`, `''`) → défauts de l'âge (âge illisible : exception, entrée isolée par `migrateInPlace`, comportement historique) ; `[]` inchangé ; autre non-tableau (chaîne, objet, nombre) → défauts de l'âge (ou `enfant` si l'âge est illisible) + warn ; clé legacy → successeurs en place, dédoublonnés, `logger.info` (id du profil, jamais le prénom) ; `updatedAt` JAMAIS bumpé (sinon 409 `stale` sur les onglets ouverts). **Écriture** (`applyModerationCategories`) : clé legacy **convertie** + warn (onglet resté ouvert), jamais rejetée. Défauts enfant/ado = les 5 historiques **+ `criminal`**, **sans `dangerous`** — décision produit après mesure (2026-09-26, Moderation 2, critère écrit AVANT : ≤ 1/50 faux positif éducatif sur 3 passes ET rappel ≥ 80 % sur un corpus de contrôle) : `criminal` 0/50 faux positif (16 leçons d'histoire/guerre comprises) et rappel 7/7 ; `dangerous` 0/50 mais rappel 5/8. Les faux positifs éducatifs de 2411 (électricité, chimie) ne se reproduisent pas sur 2603. Corpus, rapport et scripts dans `output/moderation-corpus/` (hors git) : **rejouer la mesure à chaque bump du modèle**. Les défauts sont COPIÉS à la création du profil : aucune migration des profils existants (décision produit, un parent coche la case lui-même). L'ancienne clé i18n reste pour l'historique des sources.
- **Fail-closed** (`generators/moderation.ts`) : liste bloquée non-tableau, objet `categories` absent ou catégorie **bloquée par le profil** absente de la réponse → `status: 'error'` + `logger.error` (jamais `unsafe` : ce n'est pas un contenu signalé). Seules les clés bloquées sont exigées ; clés locales inconnues ignorées (warn) ; exceptions de l'API propagées (codes actionnables conservés).
- **Statuts → HTTP** (`helpers/moderation-http.ts`, partagé serveur/front) : `moderationRejection` → `unsafe` 400 (`moderation.blocked`, ou `chat.moderationBlocked`), `error` 503 `moderation.error`, `pending` 409 `moderation.pending`, statut inattendu 503 ; `pickBlockingSource` → priorité `unsafe` > `error` > `pending` (serveur ET `blockedModerationSource` côté front). Texte libre / recherche web : `moderateUserInput` (`routes/sources.ts`), exception → 500 JSON `extractErrorCode` (plus de 500 HTML), aucune collecte si refus ; il s'appuie sur `screenUserText(client, text, categories, unsafeKey?)` (`helpers/input-moderation.ts`, source unique de la modération d'un texte fourni par l'utilisateur, sans réponse HTTP : `categories` null → accepté sans appel, refus `moderationRejection`, exceptions propagées), partagé avec la réponse orale du quiz vocal. Génération ET analyse de route passent par le même `buildGenContext` (`/generate/route` avec le modèle routeur) : même garde, dans le même ordre, avant tout appel LLM. `quiz-review` et `remediation-summary` : après validation, `scopeToOriginalQuizSources` remplace `body.sourceIds` par les sources du quiz d'origine → garde, tracker et LLM sur les mêmes sources (`[]` legacy = toutes), un `sourceIds` envoyé par l'appelant ne contourne plus la garde ; front `remediate` : pré-contrôle `checkGenerationAllowed(this, sources du quiz)`, `lang` + `ageGroup` envoyés (capturés au clic, avec le cours et la clé), un seul toast et pas de « Réessayer » sur `moderation.blocked`.
- **Statut EFFECTIF** (`helpers/moderation-http.ts`) : `profileBlockedCategories(profile, defaults, unknownAgeDefaults?)` (liste du profil si c'est un tableau, sinon défauts de l'âge, sinon `unknownAgeDefaults` : `[]` au front, défauts `enfant` au serveur) ; `effectiveModerationStatus(moderation, blocked)` promeut en `unsafe` une source persistée `safe` dont les catégories stockées valent `true` pour une catégorie bloquée (expansion legacy des deux côtés), jamais de déclassement ; **statut de garde** `gateModerationStatus(moderation, blocked)` = statut effectif d'une source vérifiée, `pending` pour une source **jamais vérifiée** (sans objet `moderation` ou sans statut : importée quand la modération était inactive, projet orphelin rattaché, donnée legacy) — elle attend sa vérification au lieu de passer ; `pickBlockingSource` / `blockingModerationStatus` / `selectChatSources` / `displayedModerationStatus` (branche modérée) raisonnent sur ce statut de garde, **réservé aux profils modérés** (le pré-contrôle front ne l'applique que si `currentProfile.useModeration`). `blockingModerationStatus` rend le statut de garde de la source choisie, jamais `undefined` pour une source non vérifiée (sinon fail-open). `awaitsModeration(moderation)` (tout sauf `safe`/`unsafe` persisté) désigne les sources à (re)vérifier, côté serveur (`settleSourceModeration`) comme côté front (pré-contrôle, ouverture de projet). Utilisé par la génération (`checkModeration` reçoit le projet déjà chargé), l'analyse de route, le chat et le front (`src/app/effective-moderation.ts` : blocage `blockedModerationSource` ET badge des sources via `displayedModerationStatus`, seulement si `currentProfile.useModeration` ; le gabarit `moderation-badge-src.html` teste `moderationStatus(src)`, jamais `src.moderation?.status`, sinon une source jamais vérifiée n'aurait pas de badge). Rattrape les sources importées pendant la fenêtre du bug (persistées `safe` avec `criminal: true`) et applique aussitôt une catégorie cochée plus tard par le parent ; rien n'est réécrit sur disque. **Ne jamais relire `source.moderation.status` pour décider d'un blocage** : passer par le statut de garde.
- **Profil et catégories actives côté serveur** (`helpers/moderation-profile.ts`, source unique des routes génération / analyse de route / chat / sources et de `selectChatSources`) : `moderationProfileOf(project, profileStore)` = profil PROPRIÉTAIRE du projet (`meta.profileId`) ou null, jamais le profil courant du navigateur ; `activeModerationCategories(profile)` = `null` si `useModeration` est faux (source importée non modérée, message non vérifié), sinon une copie de `profileBlockedCategories(profile, MODERATION_CATEGORIES, MODERATION_CATEGORIES.enfant)` — âge illisible ou hostile, liste corrompue → défauts `enfant` (fail-closed, jamais le prototype). `[]` ≠ `null` : modération active sans catégorie cochée → le chat ne vérifie pas le message, mais les sources sont modérées et leurs catégories stockées (statut effectif si le parent coche une case plus tard). **Ne jamais re-résoudre `moderationCategories ?? - **Chat** : avec `useModeration`, `selectChatSources` (`helpers/chat-sources.ts`) exclut les sources dont le statut de garde est `unsafe`/`error`/`pending` (source jamais vérifiée comprise, et tout statut inattendu) du **contexte ET des outils** ; la conversation n'est jamais refusée (notice « pas de sources ») ; seul le nombre de sources exclues est journalisé. - **Reprise des modérations** (`helpers/source-moderation.ts`, source unique : aucun `moderateContent` sur une source hors de ce module) : registre `inFlight` (`pid:sid`), une seule modération en vol par source — `moderateSourceOnce` rejoint la promesse en cours, ne lève jamais (exception → `error` persisté + `logger.error`) ; - **Réponse orale du quiz vocal** (`POST /:pid/generations/:gid/vocal-answer`, `runVocalAnswer` dans `routes/generations.ts`) : après les 4xx de validation (`lang` compris, avant tout appel), transcription (STT) puis **modération de la transcription AVANT `verifyAnswer`** avec les catégories du profil PROPRIÉTAIRE (`vocalAnswerCategories` : null si la modération est inactive ou sans catégorie cochée `[]`, comme le message du chat ; transcription vide → rien à modérer) : `unsafe` → 400 `quiz.answerBlocked` (ni vérification ni transcription dans la réponse, rien de stocké), `error` → 503 `moderation.error`, exception de la modération → 500 `extractErrorCode(e, 'moderation')` ; STT et vérification sous `runWithUsageTracking` + `persistUsage`, coût persisté quelle que soit l'issue (refus compris, `…/vocal-answer/failed` avec l'usage capté sur exception), `costDelta` dans la réponse. - **Consigne : détectée et appliquée sur les seules sources sûres** : la détection (`consigneSystem`) ne retient qu'une consigne EXPLICITE adressée à l'élève (« Je sais ma leçon si je sais… »), `keyTopics` = ses points recopiés fidèlement, `text` = son en-tête ; - **Limites connues (assumées, l'API n'ayant pas d'authentification)** : (1) un projet sans `meta.profileId` (legacy, listé pour tous les profils) est rattaché DÉFINITIVEMENT au premier profil existant qui l'ouvre (`GET /api/projects/:pid?profileId=`, envoyé par `selectProject`, `refreshConsigne` et `reconcilePendings` via `openingProfileQuery` ; `store.adoptProject` écrit project.json ET l'index et ne réattribue jamais un projet rattaché ; profil absent, invalide ou inconnu → simple lecture), puis modéré selon ce profil (ses sources jamais vérifiées comptent en attente et sont vérifiées à l'ouverture comme avant toute génération) ; seul un appel API direct sur un projet encore orphelin reste non modéré (l'API n'a pas d'authentification) ; (2) le masquage du contenu des sources est une protection d'INTERFACE : `GET /api/projects/:pid` renvoie toujours le `markdown` de chaque source et `/output/projects/<pid>/uploads/…` sert toujours les fichiers importés, l'API n'ayant pas d'authentification.

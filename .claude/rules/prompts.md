# Prompts IA — Conventions

Toutes les fonctions de prompt vivent dans `prompts.ts`. Les generators (`generators/*.ts`) les importent et composent, ils ne redefinissent pas de prompt inline.

## lang + ageGroup (obligatoire)

- Chaque prompt system/user doit accepter `ageGroup: AgeGroup` et `lang: string` en param et les propager.
- Le prompt system applique `ageInstruction(ageGroup)` — sauf `verifyAnswer` qui utilise `feedbackAgeInstruction` (calibré pour feedback binaire court, pas pour génération longue).
- Exception documentée : `consigneSystem(lang)` ne prend pas d'`ageGroup` — détection de consignes, pas génération de contenu destiné à l'élève (l'âge est hors-sujet).
- Le prompt user (ou system selon le cas) concatène `langInstruction(lang)` en fin de string.
- Inventaire des prompts où `langInstruction` ferme le SYSTEM (pas de user prompt dédié porteur de langue) : `consigneSystem` et `routerSystem` (leurs user prompts ne portent pas la langue), `chatSystem` et `websearchInstructions` (conversation/agent, pas de user prompt unique), `verifyAnswerSystem` (le user est un couple question/réponse court). Partout ailleurs, `langInstruction` ferme le USER.
- Exception documentée : `imageSystem` ne concatène PAS `langInstruction` — son énumération « génère TOUT le contenu (textes, titres…) » contredirait l'interdiction de texte dans l'image, en dernière position (biais de récence, sur le mode d'échec exact que le prompt combat). Ligne de langue dédiée à la place (« Le contenu source est en X… L'image reste purement visuelle. »), verrouillée par un test d'absence dans `prompts.test.ts`.
- `quizVocalSystem` injecte aussi `vocalRewriteRules(lang)` (règles de réécriture TTS par langue).

## Anti-leak lexical (leçon d'une régression prod)

**Symptôme observé** : le titre des fiches de révision contenait `"— Fiche de révision COMPLÈTE"`. Cause : le mot `COMPLETE` en majuscules, répété 3× dans le prompt `summarySystem` à proximité du champ `title`, était recopié littéralement par le LLM dans sa sortie. Combiné avec le few-shot `EXEMPLE` ajouté dans la PR `feat/prompts-improvements`, le pattern est devenu systématique.

**Règle** : ne JAMAIS mettre de tokens méta (qualificatifs du document : "fiche", "synthèse", "complete", "exhaustive", "révision") au voisinage d'un champ JSON que le LLM produit sous forme de texte libre (surtout `title`, `word`, `question`). Les LLM recyclent les mots emphasés du prompt, surtout en majuscules ou répétés.

**Corollaire** : éviter la **blacklist explicite** (`"pas de Fiche, Synthese, Complete"`) qui est un anti-pattern — elle réinjecte les mots qu'on veut éviter. Préférer une **règle positive** (`title = sujet du cours uniquement`) + 2-3 **exemples positifs** de bons titres.

**Verrous automatiques** : `prompts.test.ts` contient des assertions d'absence sur les formes combinées exactes (`'cree une seule fiche de revision complete'`, `'la fiche finale'`, `'avec cette fiche'`, `'resume complet du cours'`) — à maintenir si on refactore summarySystem.

## Politique titrage summary

- `data.title` produit par le LLM = **sujet du cours uniquement**, court et descriptif (ex: `"Les volcans"`, `"La photosynthese"`).
- Préfixe `"Fiche — "` (FR) / `"Note — "` (EN) ajouté automatiquement par `helpers/auto-title.ts` (export `autoTitle(type, data, lang)`, formatter `summary`) côté backend pour l'affichage en **carte liste générations** uniquement.
- **Vue détail fiche** (`src/partials/view-summary.html`, bloc `x-text="summaryData(gen).title"`) affiche `data.title` **brut sans préfixe** → le title LLM doit être auto-suffisant et lisible seul.
- Ne JAMAIS mentionner `"Fiche —"` dans le prompt : ça réinjecte le token "Fiche" à côté du champ title (anti-pattern).

## Retry prompts

Tous les messages de retry (2e appel après réponse invalide) sont **factorisés dans `prompts.ts`** — `summaryRetryUser(lang)`, `quizRetryUser({ kind, count?, lang? })`, `flashcardsRetryUser(count, lang)`, `fillBlankRetryUser(count, lang)`, `dictationRetryUser(count, lang)`, `podcastRetryUser(lang)`. Jamais de string inline dans un generator. Même discipline que le prompt initial :
- Pas d'écho des formulations problématiques (pas de « UNE SEULE fiche COMPLETE »).
- **Contrat aligné sur le system prompt** : le retry summary demande « autant que necessaire pour tout couvrir » + le champ `citations` — jamais un rabot de couverture type « 5-7 » quand le system dit « 10-25 typiquement » (bug historique corrigé). Le retry dictée reprend l'échappatoire « moins uniquement si le contenu ne contient pas assez de mots interessants » de `dictationUser` (pas de « N objets » ferme qui recréerait la tension plafond/plancher).
- **lang + count au 2e tour** : chaque retry se termine par `langInstruction(lang)` (l'invariant « langInstruction en dernier message user » vaut aussi au retry) et rappelle le count quand le contrat initial en a un. `quizRetryUser` est en object-arg (pattern `resolveVoices`, cf. CLAUDE.md) ; pas de `count` pour `quiz-review` (plage 5-10 portée par le system). `generateQuiz`/`generateQuizVocal` calculent `effectiveCount = count ?? 15` (précédent `flashcards.ts` : `count ?? 5`) passé au user prompt ET au retry.
- Chaque generator asserte le contenu de son 2e mock call contre la fonction factorisée (`generators/*.test.ts`), + verrous de contenu dans `prompts.test.ts` (describe `RETRY PROMPTS`).
- **Mécanique du retry (tous les générateurs JSON)** : le 1er parse passe par `tryParseJson` (`helpers/index.ts`) — un JSON invalide ou tronqué vaut `null`, donc `unwrapJsonArray(null) = []` → validation ratée → retry, au lieu d'une SyntaxError immédiate sans 2e essai (vécu : 1 podcast sur 2 en `llm_invalid_json`). Le parse du retry garde `safeParseJson`. Les tours ajoutés au 2e appel viennent **toujours** de `retryTurns(raw, retryPrompt)` : la réponse brute rejetée en tour assistant, **omis si elle est vide ou blanche** — l'API Mistral refuse en 400 un assistant au contenu vide (« Assistant message must have either content or tool_calls ») et accepte deux `user` consécutifs (mesuré). Échec final « après 2 tentatives » = `SyntaxError` → `llm_invalid_json` (jamais `Error` → `internal_error`). Le routeur ne retente pas : réponse inexploitable (JSON invalide, non-objet, `plan` non-tableau) → plan de secours `normalizePlan([])` + warn. Verrou commun : `generators/json-retry.test.ts` (un cas par générateur).
- **Chat, mêmes contraintes d'API** (`generators/chat.ts`, mesuré le 2026-09-27) : le modèle enchaîne ses appels d'outils, un par tour (« d'abord un quiz, puis des flashcards »), et rappelle parfois l'outil qu'il vient de lancer. Boucle bornée : `MAX_TOOL_CALLS` (3 générations) et `MAX_TOOL_ROUNDS` (3 tours), soit 4 appels LLM au plus ; le tour assistant renvoyé ne garde que les appels traités, chacun avec sa réponse (sinon 400 « Not the same number of function calls and responses ») ; un outil lancé à un tour précédent n'est pas relancé ; un nom d'outil inconnu (mesuré : « ### 3. **Quiz… » comme nom) reçoit sa réponse `unknown_tool` sans être compté ni lancé ; le dernier appel possible passe `toolChoice: 'none'` (texte garanti, mais parfois en tableau de morceaux, que `getContent` concatène) ; la réponse est le dernier texte non vide. `routes/chat.ts` n'envoie jamais un tour vide de l'historique (une réponse vide enregistrée bloquait le chat du projet) et n'enregistre pas une réponse vide qui n'a rien lancé ; le front affiche alors `chat.emptyReply`.

## Emphases MAJUSCULES

**Principe directeur (robustesse multi-modèles).** L'emphase (`IMPORTANT`, MAJUSCULES) **balise les contraintes dures** — elle n'est pas décorative. La cible n'est pas seulement un modèle fort : les prompts doivent rester fiables sur des modèles faibles ou non-anglophones (Mistral aujourd'hui, modèles chinois demain). Un modèle fort suit une contrainte sans balisage ; un modèle faible en a besoin. Recommandation officielle Mistral alignée : « écris pour quelqu'un sans contexte — il doit exécuter la tâche à la seule lecture du prompt ». **Dans le doute, GARDER l'emphase sur une contrainte porteuse.** Ne jamais « nettoyer » une emphase au motif esthétique ou d'un quota — c'est une régression de robustesse (leçon vécue : une passe « hygiène » qui a retiré des `IMPORTANT`/MAJUSCULES load-bearing, annulée).

Emphases **load-bearing** à conserver (liste non exhaustive) :
- `PAS de tableau "fiches"`, `IMPORTANT : … UN SEUL objet` (`summarySystem` — garde-fou parser `extractSummary`)
- `AUCUNE parenthese`, `UNIQUE EXCEPTION`, `OBLIGATOIRES` (`quizVocalSystem` — critique pour TTS)
- `INTERDICTION ABSOLUE DE TEXTE`, `ZERO` (`imageSystem` — critique pour génération image)
- `FABRIQUE JAMAIS`, `LISTE-LES TOUTES` (`sourceRefsInstruction` — anti-hallucination sources)
- `Ne mets PAS la source… liste-les toutes` (`quizUser`/`quizReviewUser` — réattribution + renfort volontaire, même si `sourceRefsInstruction` le dit déjà : la répétition aide un modèle faible)
- `NOUVELLES`, `MEMES`, `FACILES`, `AUTRE ANGLE`, `PEDAGOGIQUES` (`quizReviewSystem` — stratégie de remédiation)
- `Base TOUJOURS`, `n'est PAS couvert` (`chatSystem` — ancrage anti-hallucination)
- `UN MOT/EXPRESSION CLE`, `terme CLE`, `IMPORTANT` article, `DANS`/`JAMAIS`, `INCLUS` (`fillBlankSystem` — règle de l'article, piège fréquent)
- `JAMAIS un synonyme`, `UNE SEULE bonne reponse`, `MEME reponse`, `COMPLETE`, `JAMAIS le resultat` (`fillBlankSystem` — réponses justes refusées et indices qui donnent la réponse, cf. section « Textes à trous et fidélité au contenu »)
- `FIDELITE AU CONTENU`, `AUCUN chiffre, AUCUNE date, AUCUNE duree` (`factsInstruction` — faits inventés dans les explications et les indices)
- `FAUSSE d'apres le contenu ET dans la realite` (`distractorsInstruction` — distracteur vrai qui compte faux un élève qui a raison)
- `UNIQUEMENT`, `CHAQUE` (`summaryRemediationSystem` — portée + complétude)
- `IMPORTANT — … LUES A HAUTE VOIX` (`VOCAL_REWRITE_COMMON` — contexte TTS)
- `STRUCTURE OBLIGATOIRE`, `DOIT`, `AUCUN mot d'attenuation` (`verifyAnswerSystem` — fidélité du feedback binaire)
- `ne mentionne JAMAIS les sources` (`podcastSystem` — le dialogue parlé ne cite pas sa documentation)
- `AU TOTAL`, `DERNIERE` (`podcastSystem` — le schéma strict coupe à 8 répliques : sans ce rappel, le dialogue finissait sur une question de l'élève restée sans réponse, 7 fois sur 20)
- `IMPORTANT : génère TOUT` (`langInstruction` — convention cross-prompt)

Ce qui reste légitimement retirable = l'emphase **réellement décorative** sur du texte qui n'est PAS une contrainte (ex. adjectifs de style, interjections). En cas de doute sur « décoratif vs porteur », trancher **porteur** (garder). Il n'y a pas de quota « max 1-2 blocs » : le critère est la nature de ce qui est emphasé, pas le compte.

## Few-shots EXEMPLE

- **Un seul exemple par prompt** (plusieurs exemples ne font pas mieux et accentuent les biais de forme).
- **Exemples diversifiés entre prompts** (flashcards = géographie, quiz = éducation civique, etc.) — évite les biais de domaine dans l'ensemble.
- **Pas de pattern recyclable** dans la forme (ex: `"Brasilia — explication..."` avec tiret cadratin → le LLM peut template-iser "X — Y" pour toutes ses flashcards). Privilégier phrase simple.
- **Technique pédagogique transférable** dans l'explication plutôt que contenu très spécifique (ex: pour un quiz, expliquer pourquoi un distracteur est tentant, pas juste restituer un fait chronologique).

## Bloc d'exclusions (diversité inter-générations)

- Les headers du bloc « déjà généré » vivent dans `prompts.ts` (`exclusionHeader(type)`) — `helpers/diversity.ts#buildExclusionContext` ne porte que la mécanique (filtrage par type, extracteurs, cap 2000 chars).
- **Règle positive, scoped au CHOIX du contenu** (« Tu as déjà généré… propose-en d'autres ») — jamais d'impératif générique type « NE PAS RÉPÉTER » : le LLM peut l'appliquer au texte qu'il rédige. Bug observé en conditions réelles : mots masqués par `______` dans leurs propres phrases de dictée.
- La consigne de diversité vit UNIQUEMENT dans ce bloc (présent seulement quand un historique existe) — pas de phrase « tu DOIS proposer… complètement différentes » dupliquée dans les system prompts.
- Ordre des blocs user : markdown → exclusions → registre éventuel → `langInstruction` **toujours en dernier** (verrouillé par le describe `ORDRE DES BLOCS USER` de `prompts.test.ts`).
- **Podcast : l'accroche ne dépend pas du bloc** (mesuré le 2026-10-04, `output/podcast-corpus/2026-10-04/`, hors git). Lister les accroches passées AMORCE leur reprise : avec les formes alors imposées (« Tu savais que...? » ou « Imagine un instant... »), 11 podcasts sur 20 rouvraient comme un podcast déjà généré, 20 sur 20 sur une autre leçon, prénom en ouverture compris quand l'accroche exclue en avait un. Une forme tirée au sort, sans premiers mots imposés, ne suffisait pas : jusqu'à 6 reprises sur 10, et jusqu'à 8 ouvertures sur 20 par un prénom. `pickPodcastHook` tire une forme ET ses premiers mots (`PODCAST_HOOKS`, `prompts.ts`) parmi ceux qu'aucune première réplique passée ne commence déjà (`exclusionItems` relit le bloc ; mots entiers, accents et casse ignorés) ; le prompt impose ces mots et interdit d'interpeller l'autre en ouverture → 0 reprise sur 60 (deux leçons, quatre listes d'exclusions), début imposé respecté 70 fois sur 70. Un nouveau début s'ajoute à `PODCAST_HOOKS` : il ne doit pas commencer comme un autre.
- **Le bloc est lu au lancement de la génération** : deux générations simultanées du même type ne s'y voient pas. Elles passent donc l'une après l'autre côté serveur (`withSameTypeQueue`, cf. CLAUDE.md « Pending generations »), chacune relisant le projet à son tour.
- **Le bloc ne suffit pas toujours, même l'un après l'autre** (mesuré le 2026-10-07, `output/parallele-corpus/2026-10-07/`, hors git : critères écrits avant, 7 scans d'histoire avec consigne et une leçon sur les volcans, 8 paires par cas) :
  - textes à trous : le terme central de la leçon (« l'histoire », « la lave ») revenait en tête 2 à 4 fois sur 8 — le prompt veut les termes CLE, du plus simple au plus difficile ;
  - quiz avec consigne : même 1re question 4 fois sur 8, recouvrement 0,76 — l'en-tête demandait « d'autres points du contenu », la consigne la priorité à SES points. L'en-tête du quiz permet désormais « le meme point avec un autre fait ou un autre angle » ; seul, il ne changeait rien (5 sur 8) ;
  - remède déterministe (`generateFresh`, `routes/generate.ts`) : quand des séries existent, des éléments de plus (`EXTRA_WHEN_PREVIOUS` : 10 questions de quiz, 5 textes à trous), les inédits d'abord (`preferUnusedAnswers` / `preferUnseenQuestions`, `helpers/diversity.ts`), coupés au nombre demandé → 0 sur 8 partout. Quiz avec consigne : recouvrement 0,06 en direct avec 10 de plus ; avec 5, 0,36 en script et 0,45 en direct, et 0,48 sans le nouvel en-tête. Coût : le 2e quiz d'une paire prend une dizaine de secondes de plus. Le quiz vocal garde son en-tête (non mesuré).
- **Même régime pour le header consigne** : `consigneMarkdownHeader(topicsList)` vit dans `prompts.ts` (consommé par `routes/generate.ts#applyConsigne`). Instruction **explicite et emphasée** (« Concentre-toi PRIORITAIREMENT… Le contenu hors-programme peut etre utilise en complement ») : un modèle faible doit prioriser les points de la consigne **sans ignorer le reste** — ne pas raccourcir au point de perdre le sens (leçon : une version « minimale » qui retirait la consigne de priorité était une régression). Le marqueur « CONSIGNE DE REVISION DETECTEE » est référencé par `summarySystem`/`summaryUser` : ne pas le renommer.

## Détection de consigne (`consigneSystem` / `consigneUser`)

- **Consigne EXPLICITE seulement** : un texte adressé à l'élève qui dit quoi savoir ou réviser pour une évaluation (« Je sais ma leçon si je sais… », « Pour le contrôle, je dois savoir… », « À apprendre pour l'évaluation… », « Programme du contrôle »). Le contenu de la leçon, ses exercices et ses questions n'en sont pas → sans un tel texte, `found: false`. Ne jamais réintroduire « objectifs d'apprentissage » ni « programme » au sens large dans le critère : toute leçon en a, la consigne était « trouvée » partout.
- **`keyTopics` = les points de la consigne, UNIQUEMENT eux**, dans l'ordre, recopiés fidèlement (ni résumés, ni regroupés, ni complétés par un sujet pris ailleurs) : ils deviennent la priorité de toutes les générations (`consigneMarkdownHeader`, qui garde le reste des documents en complément) et la liste que l'élève relit dans le dialogue. **`text` = l'en-tête de la consigne** tel qu'écrit (évaluation, date, titre de la leçon), jamais un résumé des documents.
- **Mesuré le 2026-10-04** (`output/consigne-corpus/2026-10-04/`, hors git : critères écrits avant, corpus réel de 6 scans + photo de consigne, 3 passages) : ancien prompt 0/3 sur la consigne réelle (4 sujets hors consigne ajoutés), consigne « trouvée » 3/3 dans les 6 scans qui n'en ont pas ; nouveau prompt 3/3 partout (7 points mot pour mot, liste identique aux 3 passages) ; un quiz généré avec la consigne : 81 % des questions sur ses points, le reste sur les autres scans. **Rejouer cette mesure à chaque retouche du prompt ou changement de modèle.**

## Textes à trous et fidélité au contenu

- **Correcteur** (`helpers/fill-blank-validate.ts`, source unique du navigateur et du score serveur) : casse, accents, article de tête, typographie des tablettes (’, guillemets, œ, exposant ᵉ) et une faute de frappe sur les MOTS sont tolérés ; un nombre, une date, un siècle ou un chiffre romain doit être exact, sous toutes ses écritures (« 9 » = « neuf », « XVe » = « XV » = « 15e » = « quinzième », « -3000 » = « 3000 av. J.-C. »), sauf écriture imposée par la phrase (« en chiffres romains », « en lettres », « en chiffres » ; « Empire romain » n'impose rien ; jamais par l'indice, caché tant que l'enfant ne l'ouvre pas : « Écris-le en chiffres romains » dans l'indice faisait refuser « 5e », vécu au release-test) : seule la notation de la réponse compte alors, y compris dans `accepted`. Chaque écriture de la réponse compte : `answer`, ses parenthèses (« XVe (quinzième) », exercices anciens) et `accepted`. Jusqu'en v1.7.9, la tolérance de frappe acceptait « 1788 » pour « 1789 » et « XIVe » pour « XVe ».
- **Générateur** (`generators/fill-blank.ts`) : une seule écriture dans `answer`, les autres dans `accepted` (toujours un tableau), et tout exercice dont la phrase ou l'indice donne la réponse est écarté (`answerLeaks` : une écriture de la réponse, ou un encadrement « entre le XIVe et le XVIe ») ; 5 exercices sur 60 écartés dans la mesure finale.
- **Prompt** (`fillBlankSystem`) : le mot du contenu, JAMAIS un synonyme ; un seul mot avec son article, un nom propre, une date ou un nombre, pas une expression qu'on peut raccourcir ; UNE SEULE bonne réponse ; `accepted` = les autres écritures de la MEME réponse (chiffres ou lettres, siècle en chiffres romains ou arabes, forme courte qui suffit), seulement dans la notation imposée ; l'indice mène à la réponse COMPLÈTE sans mot de sa famille, sans calcul ni dessin des lettres, et pour un nombre, une date, un siècle ou un chiffre romain rappelle la règle du contenu (deux exemples exacts dans le prompt). Exemple JSON : un nombre (« huit pattes », accepted « 8 pattes »).
- **Fidélité** (`factsInstruction` : quiz, quiz vocal, remédiation, textes à trous, flashcards) : ce qui est présenté comme vrai vient du contenu, chiffres, dates et durées compris ; règles et méthodes reprises avec ses mots ; une comparaison n'apporte AUCUN chiffre ni date ni durée ; règle des siècles donnée (centaines + 1, sauf année ronde) : le modèle réécrivait « on ajoute 1 au nombre de centaines » en « deux premiers chiffres + 1 », faux pour 476. **Distracteurs** (`distractorsInstruction` : quiz, quiz vocal, remédiation) : FAUX d'après le contenu ET dans la réalité, jamais vrais mais moins précis, jamais une tranche qui chevauche la bonne, aucune question sur un fait que le contenu donne de deux façons. `ageInstruction('enfant')` : comparaisons du quotidien « seulement si elles sont exactes » (« de l'été à l'été suivant, 9 mois »).
- **Mesuré le 2026-10-10** (`output/fill-blank-corpus/2026-10-10/`, hors git : critères et addenda écrits avant chaque bras, leçons réelles d'Histoire et de Sciences, Large 3, 3 passages, jurys Opus à l'aveugle) : anciens prompts 24 éléments pénalisants sur 60 en textes à trous, 6 à 8 sur 60 en quiz, 3 à 4 erreurs de date ; version retenue 10 sur 55, 0 sur 60, 0 erreur de date (2 avec la lecture la plus stricte), après 4 versions (rapport : `rapport.md`). Restent : indice qui définit par un mot de la même famille, réponse longue sans forme courte acceptée. **Rejouer cette mesure à chaque retouche de ces prompts ou changement de modèle.**

## Contrat JSON

- `jsonInstruction()` fournit `"Reponds UNIQUEMENT en JSON valide."` **+ interdiction explicite de tout texte d'emballage et des balises de code** (`pas de ```) → appeler en fin de system prompt. Durci pour la robustesse multi-modèles : les modèles faibles / non-anglophones emballent souvent le JSON (préambule « Voici le JSON », fences markdown) → parse cassé. La phrase exacte `"Reponds UNIQUEMENT en JSON valide."` reste un substring stable (verrouillé par les tests) ; ne pas la modifier, seulement compléter.
- Le `Format EXACT` doit être littéralement donné dans le prompt (pas une description). Si on attend `{"items": [...]}`, le montrer.
- Invariants à protéger : `PAS de tableau "fiches"` dans summary (garde-fou contre `{"fiches":[...]}` qui casse `extractSummary`).
- `responseFormat: { type: 'json_object' }` côté client Mistral complète (ne remplace pas) l'instruction dans le prompt.
- **Exception mesurée : le podcast passe en sortie structurée stricte** (`PODCAST_RESPONSE_FORMAT`, `generators/podcast.ts` : `json_schema`, `strict: true`, speaker `host`/`guest`, texte non vide, 6 à 8 répliques). Mesure du 2026-10-04 sur `mistral-large-latest` : en `json_object`, 10 premiers appels sur 20 étaient inexploitables (2 sur 10 sans bloc d'exclusions : script vide `{"script": [ },` en 9 tokens, ou clé `"speaker"` sortie en `" "`), et la reprise n'en rattrapait pas toujours (un podcast du mode Auto en `llm_invalid_json`) ; en schéma strict, 0 premier appel inexploitable sur 310. medium et small : 0 échec dans les deux modes. Ni la température (0.7) ni `presencePenalty` 0 ne réglaient le problème. Le SDK envoie `schemaDefinition` sous `json_schema.schema` (verrou : `mistral-client-factory.contract.test.ts`). Un autre générateur qui dégénère en `json_object` : mesurer d'abord, puis le même remède ; un `maxItems` impose de dire dans le prompt comment finir dans la borne.

## Sources et citations

`sourceRefsInstruction(itemName)` factorise l'instruction anti-hallucination sur les sources pour les prompts qui produisent des références (`summary`, `flashcards`, `quiz`, `fill-blank`, `podcast`, `quiz-vocal`). À réutiliser pour tout nouveau generator qui cite des sources.

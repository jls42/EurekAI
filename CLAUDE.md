# EurekAI

Application educative IA : photo/texte/voix -> fiches + flashcards + quiz + podcast + traduction.
Concu pour un enfant de 9 ans. Powered by Mistral AI.

## Stack & Lancement

- **Backend** : TypeScript, Express, tsx (dev)
- **Frontend** : Vite + HTML + TailwindCSS + Alpine.js (src/)
- **APIs** : Mistral AI (chat, OCR, STT, TTS Voxtral, agents, moderation)

```bash
npm ci         # install reproductible depuis package-lock
npm run dev    # concurrently: tsx watch server.ts + vite -> http://localhost:5173
npm run test   # pretest quality gate + vitest
```

## Regles OBLIGATOIRES

### lang et ageGroup
Chaque route de generation et chaque appel IA DOIT recevoir `lang` et `ageGroup`.
Le frontend envoie via `getLocale()` et `currentProfile.ageGroup`. Ne JAMAIS hardcoder `"fr"` ou `"enfant"`.
- **Validés à l'entrée de TOUTE route qui les lit** (`/generate/*` via `BODY_CHECKS`, chat, recherche web, upload/voice/text/detect-consigne, vocal-answer, read-aloud) : absents → défaut de la route ; présents mais invalides → **400 `invalid_input`**, AVANT tout appel IA, toute modération et toute écriture. `lang` finit tel quel dans `langInstruction` (un code inconnu n'est pas traduit) : du texte libre y serait une injection de consignes que la modération ne voit pas. Source unique `helpers/request-validation.ts` : `isLangCode` (BCP-47 simple, ancré, sans drapeau `m` : 2-3 lettres + 2 sous-étiquettes max, ex. `pt-BR`), `readLocaleFields`, `readBodyLang`, `rejectInvalidLang` ; `isAgeGroup` vit dans `profiles.ts` (`Object.hasOwn` : `constructor`/`__proto__` refusés). Upload multipart : un refus supprime les fichiers déjà écrits par multer. Jamais ces prédicats dans `routes/generate.ts` (mocké par d'autres tests).

### i18n frontend
- Tous les textes UI via `t('cle.traduction')` — jamais de texte en dur dans les templates HTML
- Ajouter chaque cle dans les **9 fichiers i18n** : `src/i18n/{fr,en,es,pt,it,nl,de,hi,ar}.ts`
- Le test `src/i18n/i18n-sync.test.ts` verifie la synchronisation entre toutes les langues

### TTS (Text-to-Speech)
- Provider unique : Mistral Voxtral TTS (`MISTRAL_API_KEY` suffit, pas de clé supplémentaire). Le support ElevenLabs historique (hackathon) a été retiré 2026-04 faute d'intégration au niveau Mistral (voix par langue, cost tracking) — une migration one-time dans `initConfig` nettoie les `config.json` legacy (`ttsProvider`/`voices`/`eleven_*`/`mistralVoices`/`mistralVoicesSource`). Réintégration ElevenLabs envisagée plus tard au même niveau de qualité.
- `apiStatus.ttsAvailable === apiStatus.mistral` (une seule source, plus de champ `elevenlabs`).
- **Types qui exigent le TTS : source unique `TTS_DEPENDENT_AGENTS`** (`generators/auto-agents.ts` : podcast, quiz vocal, dictée — une lecture audio par mot), lue par le serveur (tri de `/generate/auto`, `TTS_AGENTS` des codes d'erreur qui en dérive) ET le navigateur. Jamais de liste `['podcast','quiz-vocal']` en dur : la dictée y manquait (bouton actif sans TTS, plan auto non filtré, échec TTS classé `internal_error`). Griser un bouton de génération avec `:disabled="ttsBlocked(type)"` + tooltip `t('gen.needsTts')` (`src/app/config.ts` : `ttsBlocked` = `usesTts(type) && !ttsReady()`, `ttsReady()` = clé d'env OU clé navigateur) ; un bouton propre à un type audio teste `!ttsReady()` (vues podcast, quiz vocal, dictée). Verrou des gabarits : `src/app/config.test.ts`.
- **Voix par langue** : `resolveVoices({ profileVoices?, lang, profileId, flow })` dans `config.ts` résout la voix finale selon la priorité : override profil non vide > sélection dynamique `selectVoices` (bucket langue, puis EN, puis any) > fallback interne. Les voix globales `mistralVoices`/`mistralVoicesSource` sont legacy, supprimées de `config.json` par `initConfig` ET rejetées avec `logger.warn` dans `saveConfig` (protection client stale entre deux restarts).
- **Liste des voix** (`listVoices`, `generators/tts-provider.ts`) : `client.audio.voices.list` (GET `/v1/audio/voices`, pagination par offset) est marqué déprécié depuis le SDK 2.7.0 au profit de GET `/v2/audio/voices` (curseur `next_page_token`, répond 200 le 2026-09-26), que le SDK n'expose pas encore ; la v1 répond toujours, sans date de retrait publiée → suppression justifiée `sonarjs/deprecation` + `NOSONAR(S1874)` sur l'appel. Migrer dès qu'une méthode v2 existe dans le SDK.
- **Appels `resolveVoices()`** : la signature impose un arg objet avec `lang: string`, `profileId: string | undefined`, `flow: VoiceFlow` (union `'podcast' | 'quiz-vocal' | 'read-aloud'` exportée depuis `types.ts`). Pas de `null` : un seul sentinel "absent" pour les call sites (cf. commentaire `ResolveVoicesArgs` dans `config.ts`). Le typechecker bloque tout call site qui oublie l'un des trois champs. `profileId` seed la **rotation déterministe** par profil (avec `langMatched`, cf. `helpers/voice-selection.ts`) — un même profil garde une identité sonore cohérente à travers les flows. `flow` n'entre **PAS** dans le seed : il existe uniquement pour **contextualiser les logs de fallback** dans `resolveMistralDefaults` (observabilité : savoir quel pipeline a tiré la voix quand on debug).

### Prompts IA (anti-leak lexical)
- Centralisés dans `prompts.ts` — les generators importent, ne redefinissent jamais de prompt inline
- **Ne JAMAIS mettre de tokens méta** (`"fiche"`, `"complete"`, `"exhaustive"`, `"synthese"`) au voisinage d'un champ JSON que le LLM produit sous forme de texte libre (surtout `title`, `word`, `question`) — le LLM recycle ces mots dans ses outputs (bug historique `"— Fiche de révision COMPLÈTE"` dans les titres)
- **Pas de blacklist explicite** (`"pas de 'Fiche'"`) qui réinjecte les mots — préférer règle positive + exemples positifs
- **Règle "title" summary** : `data.title` = sujet du cours uniquement, préfixe `"Fiche — "` ajouté par `helpers/auto-title.ts` pour la carte liste seulement ; la vue détail affiche `data.title` brut
- **Retry prompt** (`generators/summary.ts`) : même discipline que le prompt initial, pas d'écho des formulations problématiques
- **Podcast** : seul générateur en sortie structurée stricte (`PODCAST_RESPONSE_FORMAT`, `json_schema` : 6 à 8 répliques `host`/`guest`) — en `json_object`, `mistral-large-latest` rendait la moitié des premiers scripts inexploitables (mesuré le 2026-10-04) ; accroche tirée par `pickPodcastHook` parmi les débuts qu'aucun podcast précédent n'a pris (lister les accroches passées amorçait leur reprise). Mesures : `.claude/rules/prompts.md` (Contrat JSON, Bloc d'exclusions).
- Détails complets et règles sur emphases MAJUSCULES / few-shots / retry dans `.claude/rules/prompts.md`

### Codes d'erreur API (FailedStep)
- `/generate/auto` retourne `failedSteps: FailedStep[]` avec codes stables (`types.ts` : `FailedStepCode`) — jamais `err.message` brut dans la réponse HTTP (fuite potentielle clés API / URLs internes)
- **Source unique** : `types.ts` exporte `FailedStepCode`. Toute addition casse `helpers/error-codes.test.ts` (_KNOWN_CODES) tant que le nouveau code n'est pas listé → force une revue volontaire des consommateurs (UI mapping, retry policy, observabilité).
- Codes : `llm_invalid_json`, `quota_exceeded`, `upstream_unavailable` (503/529 panne backend, ou délai dépassé / connexion impossible levés par le SDK sans statut : `matchTransport`, évalué APRÈS les règles audio pour qu'un échec du TTS garde `tts_upstream_error`), `auth_required` (401/403 OU clé API locale non définie), `tts_upstream_error`, `context_length_exceeded`, `internal_error`
- Status 502 quand tous les steps échouent (réponse inclut `error: 'all_steps_failed'`), 200 sinon
- **Tous les endpoints** qui renvoient une erreur HTTP doivent utiliser `extractErrorCode(e, '<agent>')` plutôt que `err.message`/`String(e)` (cf. `helpers/error-codes.ts`) — ne pas en créer de nouveaux sans cette pratique.
- **Limiteurs** (`helpers/rate-limit.ts`) : tout 429 répond `{ error: 'rate_limited' }` (jamais de texte libre) avec `Retry-After` (secondes) ; front : `resolveError` / `mapServerErrorCode` → `errorCode.rate_limited`, refus d'un PIN → `profile.pinRateLimited` avec les minutes lues dans `Retry-After` (15 par défaut). `generalLimiter` (300/min) monté AVANT la première route `/api` (les routes de config lui échappaient) ; `aiLimiter` (60/min) monté UNE fois par `aiPathLimiter` (`AI_PATH_RE` : generate, sources, chat, detect-consigne, moderate, `generations/:gid/(vocal-answer|read-aloud)` ; drapeau `i` et barre finale tolérée, le routage d'Express 5 ignorant la casse — mesuré), avant la clé et multer — **jamais de `router.use(aiLimiter)`** dans un routeur (il comptait deux fois le chat et limitait tentatives, renommage, suppression et annulation) ; `authLimiter` (30 / 15 min) sur la seule création de profil ; `pinLimiter` (10 PIN faux / 15 min par IP) sur `PUT`/`DELETE /api/profiles/:id` : sans `pin` ni comptée ni bloquée, seuls les 403 restent comptés, au-delà 429 même pour le bon PIN. Compteurs en mémoire (un redémarrage les remet à zéro). Verrou : `helpers/rate-limit.test.ts` (vraies apps Express, port éphémère).
- **Recherche web** (`POST /:pid/sources/websearch`, `routes/sources.ts`) : au moins une source créée → 200 inchangé (array nu, ou `{ sources, failures }`) ; aucune → **422** `{ error: 'url_blocked', failures }` si la garde SSRF a rejeté TOUTES les tentatives, sinon **502** `{ error: 'all_sources_failed', failures }` (repli en échec, erreur de l'API, mélange avec des rejets SSRF), cf. `respondNoWebSources`. `failures[] = { label, code }` : `url_blocked` pour un rejet SSRF (journalisé en `warn` sans stack), sinon `extractErrorCode` de l'erreur, que le repli `fallbackWebSearchUrl` propage (il ne l'avale plus en `null` : `quota_exceeded`, `auth_required`… arrivent au front). Front : `websearchErrorCode` (`src/app/websearch.ts`) affiche le code que partagent tous les échecs s'il est parlant (≠ `internal_error`), sinon le code global, traduit par `resolveError`.
- **Uploads multipart** : tout middleware multer DOIT être enveloppé par `withUploadErrors` (`helpers/upload-errors.ts`) → `file_too_large` (413), `upload_failed` (400 : multipart invalide ou garde-fou), `internal_error` (500 : panne du stockage). Sans lui, une erreur multer part dans le handler Express par défaut (500 + page HTML avec stack hors production) et l'UI affiche « Internal Server Error ». Verrou : `routes/upload-guards.test.ts`.
- Le détail complet (stack, message) reste dans `logger.error` côté serveur
- **Traduction** : tout code stable renvoyé (`{ error: 'code' }`) a sa clé `errorCode.<code>` dans les 9 langues (verrou : `src/i18n/i18n-sync.test.ts`, qui lit les sources du serveur : `error: '…'`, constantes `ERR_*` et `ValidationError(4xx, '…')`). **Jamais de texte dans un refus** (même verrou) : « Projet introuvable », « Nom requis »… s'affichaient en français dans les 9 langues. Requête mal formée → `invalid_input` (`INVALID_INPUT`, `helpers/request-validation.ts`), la raison précise part dans les journaux (`logger.warn`, profils) ; ressource absente → `project_not_found`, `generation_not_found`, `source_not_found`, `profile_not_found` ; PIN faux → `pin_wrong` ; enregistrement vocal sans parole → `empty_transcription`. Front : `resolveError` et `mapServerErrorCode` traduisent tout code qui a sa clé, sans liste blanche (celle de `mapServerErrorCode` laissait `stale` s'afficher brut).
- **Architecture interne** : `helpers/error-codes.ts` est un re-export mince. La logique vit dans `helpers/error-code-resolution.ts` (orchestration), `helpers/error-code-rules.ts` (règles par agent), `helpers/error-matchers.ts` (matchers par pattern d'erreur — chaque matcher délimité `export function` pour contourner le parseur Lizard TS qui agglomère sinon les `function foo()` top-level consécutives).
- **Statut HTTP d'une erreur = `httpStatusOf(err)`** (`helpers/error-code-resolution.ts`) : `statusCode` (les erreurs HTTP du SDK Mistral n'ont **jamais** `status`), sinon `status`. Lire `status` seul rendait `STATUS_RULES` et le réessai applicatif inertes jusqu'en v1.7.3 : seul le message (« Status 503 … ») était analysé, et un corps qui parle de « rate limit » faisait d'un 503 un `quota_exceeded`. **Deux couches de réessai, jamais sur le même code** : le SDK rejoue ses `retryCodes` (429, 500, 502, 503, 504, sur toutes ses opérations) avec le backoff de `RETRY_CONFIG` (≤ 120 s) ; `callWithRetry` (`helpers/mistral-retry.ts`) ne rejoue QUE ce qu'il ignore (408, autres 5xx dont 520-529 de Cloudflare, placé devant l'API) + le bug de clonage du SDK. Rejouer les deux fois multiplierait l'attente (jusqu'à ~6 min sur un 429 persistant). Source : `SDK_RETRIED_STATUSES` ; verrou au bump du SDK : `mistral-client-factory.contract.test.ts`. **Bug de clonage** (mesuré le 2026-10-03, SDK 2.7.0, Node 22.18) : quand l'API répond 429 ou 503 avant d'avoir reçu tout le corps de la requête (HTTPS, gros corps : une rafale de générations), le réessai du SDK échoue sur `request.clone()` d'undici (`TypeError: unusable`), et le SDK enveloppe ce TypeError dans un `UnexpectedClientError` (`cause`) → `isSdkCloneBug` lit l'erreur ET sa cause, et `callWithRetry` reprend avec une requête neuve. Ne lire que `instanceof TypeError` laissait passer toutes les vraies erreurs (18 quiz en `internal_error` d'affilée, 0 réessai). Tests : de vraies erreurs du SDK (`SDKError`, `UnexpectedClientError` de `@mistralai/mistralai/models/errors`), jamais des `{ status }` ou un `TypeError` nu fabriqués à la main (ils validaient une branche que les vraies erreurs n'atteignaient pas).

### Cost tracking API
- **Objectif** : chaque appel Mistral **facturable** (chat, OCR, STT, TTS, agents) est instrumenté pour exposer un coût € estimé à l'utilisateur, persisté par projet. **Exception : la modération** (`client.classifiers.moderate`) n'est PAS wrappée par `tracked-client` — gratuite aujourd'hui (0 $ dans `MODEL_PRICING`) ; le JSON HTTP contient `usage` mais le SDK le retire (`ModerationResponse` sans `usage`, encore vrai en 2.7.0) → si elle redevient payante, l'instrumenter en lisant la réponse brute.
- **Source de vérité pricing** : `helpers/pricing.ts` — `MODEL_PRICING` (par prefix de modèle) + `PRICING_SOURCES` (URL doc Mistral pour scraping tarifaire) + `TOOL_PRICING` (par appel d'outil d'agent, cf. ci-dessous). Prefix matching greedy (plus long gagne, ex: `mistral-large-2512` → `mistral-large`).
- **Frais d'outils des agents** : `TOOL_PRICING` est séparé de `MODEL_PRICING` (unité « appel », pas un préfixe de modèle ; ne PAS en faire une `BillingUnit` : cela casserait les `satisfies Record<BillingUnit,…>` de `cost-calc`, le `never` exhaustif de `src/app/model-pricing.ts` et `scripts/update-pricing.ts`) : `web_search` 0,03 $/appel, `image_generation` 0,10 $/image (mistral.ai/pricing/api, vérifiés le 2026-09-26, **non surveillés** par `update-pricing` → re-vérifier à la main). `wrapAgent` capte `toolCalls` depuis `usage.connectors` (compteur d'appels par outil) s'il reste un compteur valide, sinon en décomptant les sorties `tool.execution` par `name` — jamais les deux ; seuls les entiers finis ≥ 0 sont gardés ; outil sans tarif → `logger.warn` dans `tracked-client`, compté 0 $ (`cost-calc` reste pur). `connectorTokens` (`usage.connector_tokens`) est HORS `prompt_tokens` (mesuré : total = prompt + completion + connector) → compté au tarif d'entrée du modèle de l'agent (estimation prudente). `calculateCost` = coût modèle + Σ `perCall` × n (frais d'outil dus même sans tarif modèle) ; `aggregateUsage` fusionne `toolCalls` et `connectorTokens` ; `buildCostBreakdown` ajoute `N × outil × $X/call` et `N tool tokens in`. **Limite connue** : `conversations.start` est rejoué par le backoff du SDK (429, 500, 502, 503, 504), puis par `callWithRetry('agent')` sur les transitoires que le SDK ignore (408, autres 5xx dont 52x), et seule la réponse finale porte un `usage` → les frais d'outils d'une tentative échouée (ex. une image générée, 0,10 $, avant un 5xx) ne sont pas captés, et une image peut être facturée deux fois.
- **OCR 3/OCR 4 + medium** : `MODEL_PRICING` distingue `mistral-ocr-4` ($4/1000 pages : OCR 4.1 `mistral-ocr-4-1`, défaut, et l'ancien OCR 4.0 `mistral-ocr-4-0`, retiré le 2026-09-30, même `billing_model_name`) de `mistral-ocr` ($2/1000, OCR 3 `mistral-ocr-2512`) — le greedy-prefix (plus long gagne) résout le tarif sur l'**id capturé** par `tracked-client`, qui n'est PAS forcément daté (mesuré 2026-09-25) : chat/OCR/STT → `response.model` = l'id **demandé tel quel, alias compris** ; TTS → `request.model` ; agents → `mistral-large-latest` forcé ; seule `/v1/moderations` renvoie l'id résolu daté. **Conséquence** : un alias repointé vers une version d'un autre prix garderait l'ancien tarif en silence (ex. `mistral-ocr-latest` sert OCR 4.1 mais tomberait sur le préfixe `mistral-ocr` = tarif OCR 3 — d'où son rejet par `normalizeOcrModel`) → envoyer un id versionné dès que le prix varie dans une famille, avec une clé `MODEL_PRICING` distincte. `mistral-medium` ($1.5/$7.5 /M tokens) ajouté. **Tarifs affichés dans les sélecteurs Réglages** via `src/app/model-pricing.ts` (`modelPriceLabel` dérive de `MODEL_PRICING`, seul le suffixe d'unité est traduit → zéro duplication de prix dans l'i18n ; `toFixed(2)` sur tokens).
- **Mistral Large 4 en option** (`MISTRAL_LARGE_4 = 'mistral-large-4-0'`, `helpers/chat-models.ts`, sélecteur « Génération » des Réglages ; Large 3, `mistral-large-latest`, reste le défaut recommandé) : tarif public de 1,36 $ / 4,18 $ par M tokens (×2,7 et ×2,8 par rapport à Large 3) sous sa propre clé `mistral-large-4` ; la promotion de lancement (-50 % pendant 2 semaines à partir du 2026-10-06, sans date de fin publiée) n'est pas reportée, le coût affiché est donc surestimé jusqu'à sa fin. `update-pricing` lit aussi une ligne de prix en promotion (tarif public barré en tête). **Large 4 raisonne par défaut**, contrairement à Large 3, Medium 3.5 et Small 4 : mesuré le 2026-10-08 sur 3 questions de quiz, 907 tokens de sortie en 30 s (réponse `[thinking, text]`), contre 123 en 2,7 s avec `reasoningEffort: 'none'`. `withReasoningDefault`, appliqué par `wrapChatComplete` (`tracked-client`) à toute requête de chat, envoie donc `reasoningEffort: 'none'` aux familles de `REASONING_BY_DEFAULT` quand l'appelant ne choisit rien. Qualité non mesurée sur nos générations : la mesurer (protocole OCR : critères écrits AVANT, vraies leçons, plusieurs passages) avant d'en faire le défaut.
- **Chaîne de calcul** : `helpers/tracked-client.ts` wrappe le client Mistral (capture `ApiUsage`) → `helpers/usage-context.ts` (AsyncLocalStorage pour propager l'usage dans les pipelines async) → `helpers/cost-calc.ts` (conversion usage → € selon l'unité : `tokens` / `characters` / `pages` / `audio-seconds`, + frais par appel des outils d'agents) → `helpers/cost-persist.ts` (écriture dans `Project.costLog` + mise à jour `totalCost`) → `helpers/cost-middleware.ts` (injection du `costDelta` dans la réponse HTTP). **Modèle sans tarif** (`resolvePricing` nul) : compté 0 $, et `persistUsage` n'écrit rien pour un coût nul → `tracked-client` émet `logger.warn('cost', 'model without pricing: <id> ($0)')` à chaque capture (même régime qu'un outil d'agent sans tarif) ; ajouter l'id à `MODEL_PRICING`. Un tarif explicite à 0 $ ne déclenche rien.
- **Contrat endpoint** : les réponses `/generate/*` et `/sources/*` décorent l'objet retourné (Generation ou Source) avec `estimatedCost: number`, `usage: GenerationUsage`, `costBreakdown: string[]`. Parmi les `/generate/*`, **seul** `POST /generate/route` renvoie un champ top-level `costDelta: number` (coût du routage seul) — les autres exposent leur coût via `gen.estimatedCost` uniquement. Hors `/generate/*`, un `costDelta` top-level (coût de CET appel, que le front ajoute au total du projet via `addCostDelta`) est renvoyé par le chat (`{ reply, …, costDelta? }`), la lecture à voix haute (`{ audioUrl, costDelta? }`), **`POST /:pid/detect-consigne` → `{ consigne, costDelta }`** (`consigne` = consigne persistée ou `null`, `costDelta` toujours un nombre, 0 sans usage facturable ; libellé costLog `…/detect-consigne` → « Détection de consigne », détection de fond comprise) et **`POST /:pid/generations/:gid/vocal-answer`** → `{ correct, feedback, transcription, costDelta? }` ou, sur un refus, `{ error, costDelta? }` (STT + vérification ; présent dès que non nul, refus compris : la transcription est facturée ; libellé `…/vocal-answer` → « Réponse vocale »). `GET /projects/:pid` retourne le projet enrichi de `totalCost` (somme calculée depuis `costLog[]`) + `costLog[]` historique.
- **Règle OBLIGATOIRE** : tout nouvel appel Mistral DOIT passer par `tracked-client` (jamais `new Mistral(...)` direct dans un generator). Sinon le coût échappe au tracking silencieusement — bug observabilité invisible côté UI.
- **Test de contrat du SDK** (`helpers/mistral-client-factory.contract.test.ts`, à faire passer à chaque bump de `@mistralai/mistralai`) : VRAIE instance construite par `buildTrackedClient`, seul `fetch` est stubbé (le `DEFAULT_FETCHER` du SDK le lit à chaque appel) → vérifie que les accesseurs de sous-clients restent mis en cache (`client.chat === client.chat` : condition du remplacement des méthodes par `tracked-client`) et que `runWithUsageTracking` capte l'usage de chat, STT, OCR, TTS et agents (réponses agents `web_search` / `image_generation` capturées en réel). `tracked-client.test.ts`, lui, tourne sur un faux client et ne voit pas une régression du SDK.

### Clé API Mistral (multi-source, navigateur)
- **Objectif** : `.env` peut être **vide** ; l'utilisateur saisit sa clé dans l'UI, **stockée dans son navigateur** (jamais sur le disque serveur), envoyée **par requête**. Clé **globale navigateur + override par profil**. Env = fallback déploiement (ECS/k8s).
- **Source UNIQUE de construction** : `helpers/mistral-client-factory.ts` — `buildTrackedClient(apiKey)` (track-once : `trackClient` appelé 1×/instance), `resolveApiKey(req)`, `resolveClient(req)`, `requireKeyMiddleware` (pré-multer), `keyFingerprint`. **Plus aucun `new Mistral(...)` / `trackClient(...)` hors de ce fichier** (le singleton `server.ts` a disparu). Le client header n'est **PAS caché** (la clé utilisateur ne reste pas en mémoire) ; seul l'`envClient` est singleton (warmups + fallback).
- **Précédence** : navigateur résout **profil > globale navigateur** (cf. `src/app/api-key.ts` `resolveRecord`) et envoie le header ; serveur résout **header > env** (`resolveClient`). Soit **profil > globale navigateur > env**.
- **Anti-facturation silencieuse de l'hôte** : un header présent mais **malformé** ⇒ `400 invalid_api_key`, **jamais** de fallback env. Le fallback env n'est utilisé que si le header est **strictement absent**. Validation `validateKeyFormat` : printable ASCII sans espace/contrôle (anti-CRLF, le header finit en `Authorization: Bearer` vers Mistral).
- **`EUREKAI_REQUIRE_USER_KEY=true`** : désactive le fallback env pour les requêtes IA (déploiement exposé) ; `getApiStatus()` met alors `mistral`/`ttsAvailable` à false ET expose `requireUserKey` → le frontend **force le gate** (sinon il sauterait l'onboarding puis se prendrait des 401).
- **Auth-first** : chaque handler IA résout la clé **AVANT** toute validation/IO (donc avant `addPendingEntry` → pas de pending tracker orphelin). Pour `/generate/*` la résolution est dans le gate (`buildGenContext`/`handleGeneration`) ; pour `quiz-review`, AVANT `validateQuizReviewInputs`. **Pré-multer** (`requireKeyMiddleware`) sur les 3 uploads (`sources/upload`, `sources/voice`, `generations/:gid/vocal-answer`) → aucun fichier temporaire écrit sans clé.
- **`/generate/auto`** : le split audio se base sur le **client effectif résolu** (la même clé fait chat ET TTS Voxtral), plus sur `getApiStatus().ttsAvailable` (env-only, faux avec une clé navigateur + `.env` vide).
- **Coalescing consigne** keyé `pid+keyFingerprint` (`routes/sources.ts`) : deux profils/clés sur le même projet ne partagent pas le scan (sinon le replay facturerait la mauvaise clé).
- **Rate-limit** : couverture `aiLimiter` élargie à `detect-consigne`, `moderate` (sous `/:pid/`, hors `/sources/`), `vocal-answer` et `read-aloud` (sous `generations/:gid/`), `/api/providers/*` (validate) et `/api/config/voices` — toutes appellent Mistral. `POST /:pid/sources/moderate` est sous `/sources/` : déjà couvert. Détail des limiteurs : section « Codes d'erreur API ».
- **Tâches de fond hors requête** (reprise des modérations au démarrage) : `getBackgroundClient()` = client env seulement si `envFallbackAllowed` (clé d'env présente, pas `EUREKAI_REQUIRE_USER_KEY=true`), sinon `null` — **jamais une clé utilisateur**, qui n'existe que le temps de sa requête.
- **`POST /api/providers/mistral/validate`** : **toujours 200** `{ status }` (`ok|invalid|quota|network|missing`), `allowEnv:false` (une clé vide ne valide pas l'env). `/api/config/voices` : `[]` si aucun client résolu (jamais `setVoiceCache([])`), 400 si header malformé.
- **Header front** : `withAiHeaders(init)` (`src/app/ai-fetch.ts`) décore **tous les call sites IA** — `fetch(url, withAiHeaders(init))` **préserve le shape `fetch(url, …)`** attendu par l'analyse SSRF (cf. Sécurité), **jamais de `Content-Type`** (uploads FormData), **omet les 2 headers** si clé vide/malformée (→ fallback env). Tout nouveau call site IA DOIT l'utiliser.
- **Redaction logs** : `helpers/redact.ts` (appelée dans `helpers/logger.ts`) masque les **champs sensibles connus** (`authorization`, `x-eurekai-ai-key`, …) + la **valeur de la clé env** ; honnête : ne tente PAS de scrubber une clé inconnue d'un texte libre. Défense primaire = ne jamais logger la clé/headers à la source.
- **Stockage navigateur** (`src/app/api-key.ts`) : AES-GCM avec **master key non-extractable auto-générée dans IndexedDB** (secure context) ; `KeyRecord` chiffré (`{encrypted:true,iv,ct}`) ou clair (`{encrypted:false,value}`) en `localStorage` (slots `sf-api-keys-global`, `sf-profile-api-keys`). Hors secure context / IndexedDB bloqué (incognito) → **fallback clair derrière consentement explicite** (UI), **re-chiffré** au retour en secure context. Master key perdue → `purgeKeyring` + gate. Clé purgée à la suppression du profil. `selectProfile` est **async** (charge la clé avant les fetchs IA).
- **HTTPS local** (`scripts/gen-cert.sh` : mkcert sinon openssl) : si `HTTPS_KEY`/`HTTPS_CERT` définis, Express **et** Vite servent en HTTPS → secure context sur tablette/LAN (le chiffrement IndexedDB marche partout) + clé chiffrée en transit. `localhost` est déjà un secure context (rien à faire). Reverse-proxy : **ne pas logger** `X-EurekAI-AI-Key`.
- **Modèle de menace (honnête)** : protège la **fuite disque serveur** + le **transit** (HTTPS) + un dump simple du stockage navigateur en secure context (réduit l'exposition, **pas un coffre-fort**). NE protège **pas** d'un **XSS** (CSP `unsafe-inline+eval`) ni d'un serveur compromis au runtime. `/api/*` n'a **pas d'auth** → avec fallback env, l'instance est un proxy IA ouvert (atténué par `EUREKAI_REQUIRE_USER_KEY`).

### Persistance config.json
- **Dans `config.ts`**, toute écriture de `config.json` DOIT passer par le helper interne `persistConfig()` (jamais `writeFileSync(configPath, …)` direct). Sinon le backup `.corrupt.bak` n'est pas créé avant overwrite d'un fichier corrompu préservé → perte silencieuse du contenu user original. Ne s'applique pas aux fichiers ≠ `config.json` (logs, caches, etc.).
- Le flag module `lastLoadFailed` tracke l'état. Reset à `false` après tout `writeFileSync` réussi de `persistConfig`, indépendamment du succès du backup — un seul `.corrupt.bak` par cycle corrompu → restore (idempotence via `existsSync` dans `backupCorrupt()`).
- **Rejection legacy à saveConfig** : tout préfixe de champ migré one-time (actuellement `ttsModel: 'eleven_*'`) doit être rejeté côté `saveConfig` aussi, pas seulement dans `migrateLegacyElevenLabsFields`. Sinon une UI pré-PR ou client automatisé peut POSTer la valeur legacy entre 2 restart → fenêtre d'incohérence opaque. Pattern : `logger.warn` + garder la valeur courante (déjà non-legacy après boot), jamais reset vers DEFAULT.

### OCR confidence scores
- **Type** : `OcrConfidence = { average: number }` dans `types.ts` — stocké en `Source.ocrConfidence?` pour les sources PDF/image.
- **Extraction** : `generators/ocr.ts` passe `confidenceScoresGranularity: 'page'` et `includeBlocks: false` (épingle : le défaut vaut `true` côté API et dans le SDK ≥ 2.6.1, donc dans la 2.7.0 installée → sans elle, payload ~×3,6 inutilisé) à l'API Mistral OCR puis `extractConfidence()` (interne, non exporté) moyenne les `averagePageConfidenceScore` des pages, clampé dans `[0,1]`.
- **Fichier déposé chez Mistral** : `ocrFile` enchaîne upload → `ocr.process` → `files.delete`, la suppression dans un `finally` (sinon la copie du document reste stockée chez Mistral quand l'OCR échoue ; échec de suppression journalisé, jamais propagé). L'API Files renvoie le **même `fileId` pour un contenu identique** (mesuré) : deux OCR concurrents du même fichier (« Importer quand même » un doublon en cours d'OCR, deux onglets) partageaient le fichier distant et la suppression de l'un cassait l'autre → `ocrFile` est sérialisé par contenu via ``withKeyedLock(`ocr:${sha256}`, …)`` (`helpers/keyed-lock.ts` : file FIFO par clé, une erreur ne bloque pas la file, clé retirée de la table après son dernier appel). Contenus différents → en parallèle. **Course connue (mesurée le 2026-09-30, non corrigée)** : renvoyé moins d'une vingtaine de secondes après la suppression par l'appel précédent, un contenu identique reçoit le `fileId` en cours de suppression → OCR en 400 (« could not be found or may have expired », code 3310) ou 422 (« Could not get file », code 1901) ; `withKeyedLock` enchaîne justement ces appels. Rare dans l'app (réimport quasi immédiat du même contenu) ; parade envisagée : nouvelle tentative différée de `uploadAndProcess` sur ces deux codes.
- **Tiers UI** : `src/app/helpers.ts` expose la méthode AppContext `ocrConfidenceTier(src: Source)` → `'high' | 'medium' | 'low' | null` (seuils ≥0.9 / ≥0.7, sinon `'low'`, `null` si `src.ocrConfidence` absent ou non-finite). NB : la méthode prend un `Source` complet (pas un `score: number`) — utiliser `src.ocrConfidence?.average` en amont si tu n'as qu'un nombre.
- **Règle** : quand un score est bas, ne PAS bloquer la génération — afficher le badge warning et laisser l'utilisateur décider (les scores bas viennent souvent de scans de mauvaise qualité, pas d'un vrai problème de contenu).

### Dédup sources (ré-import d'un fichier déjà importé)
- **Objectif** : éviter les doublons silencieux + la double facturation OCR. Chaque `Source` porte `contentHash` (sha256 du fichier brut, calculé dans `routes/sources.ts` `hashFileContent` AVANT l'OCR).
- **Double détection** : pré-check **client** (`src/app/source-dedup.ts` `hashFile` via Web Crypto — **feature-detect `crypto?.subtle`**, retourne `null` en contexte non sécurisé HTTP-LAN ; `findExistingDuplicate` par hash, fallback `filename` pour les sources d'avant la feature) **+ garde serveur** en filet (compare aux `contentHash` persistés + intra-batch, `unlink` du fichier multer orphelin). Le garde serveur est un read-then-act (**TOCTOU**, pas un verrou) et ne marque un hash « déjà importé » qu'**après persistance réussie**.
- **Contrat réponse `/sources/upload`** : **array nu** en full success (historique préservé) ; objet `{ sources, failures?, duplicates? }` dès qu'il y a un échec ou un doublon ; **200** (pas 500) quand le lot ne contient que des doublons. `req.body.allowDuplicates === 'true'` **strict** (jamais `Boolean("false")`).
- **UX** : décision **par fichier** dans la liste d'upload (statuts `'hashing'`/`'duplicate'` ; le getter `uploading` inclut `'hashing'` mais PAS `'duplicate'`) — `retryFile`/`dismissFailedFile` acceptent `'duplicate'` (« Importer quand même » = re-upload avec `allowDuplicates`, « Ignorer » = dismiss).

### Médias des générations (MP3/PNG/JPEG sous `output/projects/<pid>/`)
- **Source unique** : `helpers/generation-media.ts`. Tout média écrit prend son nom de `uniqueMediaName(prefix, ext)` (`<prefix>-<Date.now()>-<8 hex>`) et son URL de `mediaUrl` — **jamais `Date.now()` seul** : deux générations parallèles du même type écrivaient le même fichier dans la même milliseconde et s'écrasaient.
- **Suppression d'une génération** : `store.deleteGeneration` renvoie la génération retirée (`null` → 404), puis la route appelle `cleanupDeletedGeneration` (best-effort, ne lève jamais) : médias listés par `generationMediaUrls` (table d'extracteurs exhaustive par type : un nouveau champ média s'y déclare, sinon il reste orphelin) **sauf** ceux qu'une autre génération du projet référence encore (collisions d'avant les noms uniques), + balayage de `read-aloud-<id8>-*.mp3` (`readAloudPrefix`, aussi utilisé par l'écriture) : la lecture des flashcards n'est jamais référencée, une section relue remplace son URL sans supprimer l'ancien fichier. Pas de balayage si une autre génération partage le préfixe.
- **Garde de chemin** : toute suppression passe par `mediaFileName(url, pid)` — uniquement `/output/projects/<pid>/<nom simple>.(mp3|png|jpg)` du projet visé ; URL externe (image hébergée par Mistral), autre projet, `uploads/` ou traversée → ignorée.

- **Génération qui n'aboutit pas** : registre `helpers/media-ledger.ts` (AsyncLocalStorage, calqué sur `usage-context.ts`). `saveAudioFile` et l'illustration appellent `recordMediaUrl` — **tout nouvel écrivain de média DOIT l'appeler** (sans effet hors génération, ex. lecture à voix haute). `runWithMediaLedger(projectDir, pid, fn)` supprime lui-même les fichiers écrits si `fn` lève (échec partiel : quiz vocal en échec à la question N) ; `routes/generate.ts` `runWithUsageAndMedia` l'imbrique sous `runWithUsageTracking`, un contexte par génération ET par étape `/generate/auto`. Promotion refusée (`cancelled`/`failed`/`missing`) ou générateur qui renvoie null → `deleteMediaFiles(mediaUrls)`.
- **Pas de dossier fantôme** : `getProjectDir` ne crée rien (le dossier existe depuis `createProject`) et `getUploadDir` ne crée que `uploads/`, **sans récursivité** : une écriture après suppression du projet lève ENOENT au lieu de le recréer. - **Image** : les fichiers générés chez Mistral (`fileId`) sont supprimés après téléchargement (`finally`, échec journalisé en warn : gratuit, jamais bloquant). La conversation part avec `store: false`, comme celle de la recherche web (`generators/websearch.ts`) : sans lui, Mistral garde la conversation et le texte de la leçon (251 conversations d'agent sur le compte le 2026-09-27). En contrepartie, il n'y a plus d'historique à relire chez Mistral : ce qui sert au diagnostic se journalise à la source. **Plusieurs appels de l'outil pour une illustration : deux causes distinctes**, mesurées le 2026-09-27 sur les 162 historiques d'illustration que Mistral gardait :

### HTML interactif
- Ne JAMAIS imbriquer de `<button>` dans un `<button>` (HTML invalide, casse le layout)
- Utiliser `<div role="button" tabindex="0" @click @keydown.enter>` quand le conteneur cliquable contient des boutons enfants
- **Jamais de référence de fonction brute dans une directive évaluée hors événement** (`x-show`, `x-if`, `x-text`, `x-html`, `:attr`) : Alpine APPELLE toute fonction que renvoie l'expression, puis la rappelle à chaque changement de l'état qu'elle lit. `x-show="toast.retryFn"` relançait l'action d'un toast d'erreur dès son affichage (vécu : image régénérée 29 ms après son échec, 0,10 $), puis à chaque nouvel échec : boucle sans fin sur une erreur persistante (réseau coupé, 429), sur les 16 appels qui passent un réessai. Tester la présence : `x-show="!!toast.retryFn"` ; appeler seulement dans `@click`. Verrou : `src/app/toast.test.ts` (parcourt tous les gabarits, noms en `Fn`/`Callback`/`Handler`).
- **Tout `@click` doit avoir son équivalent clavier** (`@keydown.enter`, ou `@keydown.escape[.window]` pour un fond de surcouche / une fermeture) : sans lui, l'élément est inatteignable au clavier ET SonarQube le remonte en **bug** `Web:MouseEventWithoutKeyboardEquivalentCheck` (rating fiabilité B → quality gate rouge). Sonar reconnaît la syntaxe Alpine `@keydown` : pas besoin d'exclusion, le vrai correctif suffit. Ajouter `focus-ring` pour que le focus reste visible.
- **Entrée qui valide un champ de dialogue : `@keydown.enter.prevent`**. Le handler ferme le dialogue sur le keydown, le focus revient au bouton qui l'a ouvert, et le keypress d'Entrée qui suit (Chrome active un bouton sur le keypress) cliquait ce bouton : la demande de PIN se rouvrait aussitôt après validation (vécu au release-test du 2026-10-04, « Afficher (parent) », « Espace parent »…). `.prevent` sur le keydown supprime le keypress. Verrou : `src/dialog-templates.test.ts` (tout `@keydown.enter` des `dialog-*.html` porte `.prevent`).
- Les boutons de generation dans view-sources sont dynamiques via `x-for` sur `categories` — ne pas hardcoder
- **Nom accessible qui contient le libellé visible (WCAG 2.5.3)** : un `:aria-label` sur un bouton qui affiche du texte reprend les MÊMES expressions que ses `x-text` (bouton qui affiche `t(cat.labelKey)` → `t('a11y.generateCategory', { category: t(cat.labelKey) })` ; pastille de stats → compteur compris). Libellés de la forme « Verbe : {category} » (`a11y.generateCategory`, `a11y.viewCategory`, `a11y.cancelGeneration`), sans article : « Générer des Fiche de révision » ne s'accordait pas. Bouton icône seule : `:aria-label` explicite + `aria-hidden="true"` sur le SVG décoratif. Interrupteur : `<button type="button" role="switch" :aria-checked="String(!!x)" :aria-label="…">`. Verrou : `src/a11y-templates.test.ts`.
- **RTL (arabe)** : `ml-*`/`mr-*` et `translate-x-*` sont PHYSIQUES → marges logiques (`ms-*`, `me-*`) et variante `rtl:` pour les translations (`translate-x-6 rtl:-translate-x-6` : Tailwind 4 la génère en `:where(:lang(ar)…, [dir=rtl], [dir=rtl] *)`, placée après la règle de base, qu'elle remplace). Sinon le curseur d'un interrupteur ou une marge part du mauvais côté.

### Pending generations & notifications

Cycle de vie des générations en cours :

- **Refresh / switch profil ≠ cancel**. Invariant absolu : la fermeture du socket HTTP côté client (refresh, switch onglet, switch profil, navigation, perte réseau) **ne déclenche AUCUN cancel serveur**. La génération continue, persiste son résultat en `completed` même si `res.json()` part dans le vide. Le seul chemin d'annulation = `POST /api/projects/:pid/generations/:gid/cancel` explicite. Ne JAMAIS brancher `req.on('close')` pour annuler une génération.
- **N générations du même type en parallèle** : re-cliquer un bouton lance une génération de plus (`canStartGenerate` ne verrouille PAS sur `loading[type]`). `loading[type]` **reste booléen** ; il n'est libéré (cleanups single/all/auto + cancel) que s'il ne reste AUCUN autre pending du type via la fonction pure **`pendingOfTypeExists(pendingById, type)`** (`src/app/pending-utils.ts` — module dédié pour rester hors du `vi.mock('./helpers')` des tests ; param `| undefined` pour tolérer un state partiel). Les boutons des 9 vues sont **statiques cliquables** (pas de `isLoading` sur leur `:disabled`) ; les N pendings restent visibles/annulables via les chips (1 par gid). Pas de debounce (il bloquait des retries légitimes).
- **Anti-flood : au plus `MAX_PARALLEL_PER_TYPE` = 3 générations du même type en cours** (`src/app/pending-utils.ts`, vécu le 2026-10-03 : ~18 appuis en 3 s d'une enfant sur « Quiz » → 18 générations, refusées en partie par Mistral, 18 toasts d'erreur). Plafond par NOMBRE, jamais par délai (double-clic = 2 générations, réessai après échec possible : une génération échouée ne compte plus). Compté dans `runSingleGenerate` (`src/app/generate.ts` : clics des vues, version facile à lire, « Réessayer ») = `countPendingOfType(pendingById, type)` (cet onglet + autres onglets/appareils du projet via SSE) + **réservations** `launchingByType[type]` ; au-delà → toast **info** `toast.generationBusy`, rien n'est lancé. Piège : le pré-contrôle de modération (`ensureGenerationAllowed`, jusqu'à 8 s) passe AVANT le pending optimiste → la réservation est prise de façon SYNCHRONE au clic (`reserveLaunch`), gardée pendant l'attente, et rendue (`releaseLaunch`) dans le même bloc synchrone que la création du pending (aucun appui ne s'intercale) ou sur un refus ; `resetSession` vide la map (jamais de compteur négatif). Sans la réservation, tous les appuis d'une rafale passaient (verrou : tests « rafale » de `generate.test.ts`, qui échouent sans elle). Hors champ : Auto (bouton désactivé par `isGenerating()`), remédiation (`reviewing`), chat (`chatLoading`), API (aucun plafond serveur).
- **gid généré côté client** (`crypto.randomUUID()` dans `src/app/generate.ts`), passé au backend via `body.gid`. Permet `abortControllersByGid[gid]` immédiat et identifiant stable utilisable au moment du payload 200 fallback ou de l'event SSE. Le backend valide UUID v4 STRICT (`readClientGid` dans `routes/generate.ts` — version nibble = `4`, variant nibble dans `[89ab]`, aligné sur la regex client `confirm.ts:GID_UUID_V4`) ou retombe sur `randomUUID()` en cas de gid invalide. Pour `/generate/auto` (batch), la route NE LIT PAS `body.gid` : chaque step reçoit un gid serveur propre, car un body.gid global serait incohérent avec N générations.
- **Race promote/cancel** : `store.promoteToGeneration` retourne `PromoteResult = { kind: 'promoted', generation } | { kind: 'cancelled' } | { kind: 'failed', code } | { kind: 'missing' }`. Le handler dispatche : `200 generation` si promoted, `409 PromoteErrorResponse` (`types.ts`, `PromoteErrorOutcome = 'cancelled' | 'failed'` — pas `'missing'`) sinon. **Le `kind: 'missing'` du store est remappé server-side vers `error: 'failed'` côté wire** (source unique `classifyPromoteFailure` dans `routes/generate.ts` ; une étape de `/generate/auto` le rend en `internal_error` via `pickAutoStepFailureCode`) car `'missing'` = symptôme bug observabilité (entry retirée du tracker entre cancel et promote), surfaceable seulement par `logger.error` (Sentry), jamais comme code applicatif côté client. Le type HTTP est découplé du discriminant store pour qu'un futur rename de `kind` ne casse pas le client. Plus de réponse 200 fantôme quand un cancel arrive pendant que Mistral travaille.
- **Boot sweep** : `store.cancelAllPendingsAtBoot()` au démarrage marque tous les `pendingTracker[].status === 'pending'` comme `cancelled`. Pas de TTL — par construction, tout pending sur disque vient d'un process mort. Si `getProject(meta.id)` retourne null (project.json corrompu), `logger.error` dédié (niveau **error volontaire** : project.json corrompu = bug observabilité critique, pas un warn) pour signaler les pendings ghost laissés en place. Le tracker est aussi pruné à chaque save : `pruneTrackerIfNeeded` applique en permanence l'intersection **max 50 terminaux ET ≤ 7 jours d'âge** (un terminal gardé doit satisfaire les deux contraintes ; les pendings actifs ne sont jamais prunés). Appelé sur **chaque save**, pas seulement quand `length > 50`, sinon des terminaux > 7j s'accumulent silencieusement sous le seuil.
- **`pendingTracker` séparé de `generations[]`** dans `ProjectData.results` (`types.ts`). Évite de polluer `generations: Generation[]` avec des entrées sans `data`. Promotion = remove du tracker + push dans generations atomique dans le même `saveProject`. Les terminaux ne suivent pas ce chemin : `markPendingFailed`/`markPendingCancelled` (et le helper privé `replacePendingWithTerminal`) remplacent l'entrée par index avec l'arm terminale et la gardent jusqu'au pruning.
- **`PendingTrackerEntry` est une discriminated union sur `status`** (`types.ts`) : `PendingTrackerEntryActive` (status: 'pending') | `PendingTrackerEntryTerminal` (status: 'failed' | 'cancelled', `failureCode` + `completedAt` OBLIGATOIRES). Conséquence : `markPendingFailed`/`markPendingCancelled`/`cancelAllPendingsAtBoot` ne peuvent PAS muter `entry.status` in-place — ils construisent un nouvel objet terminal et remplacent par index dans le tracker (cf. `replacePendingWithTerminal`). Ferme à compile-time l'état impossible `{status: 'pending', failureCode: 'cancelled'}`.
- **SSE format obligatoire** sur `GET /api/projects/:pid/events` : `event: generation\ndata: {...}\n\n`. La ligne `event:` est obligatoire pour matcher `addEventListener('generation', ...)` côté client. Sans elle, l'event tombe sur le canal `'message'` générique. Heartbeat `: keep-alive\n\n` toutes les 25s, avec compteur `HEARTBEAT_MAX_CONSECUTIVE_THROWS=3` pour cleanup forcé si `req.on('close')` ne fire jamais (bug Node socket half-open). Le payload SSE est typé `GenerationEvent` (`types.ts`), discriminated union sur `status` partagée serveur ↔ client : `generation` n'existe que sur `'completed'`, `failureCode` que sur `'failed'`/`'cancelled'`.
- **Idempotence à 2 niveaux côté client** :
  - `appendNotification(profileId, {eventKey, ...})` dans `src/app/notifications.ts` est idempotent par `eventKey` via le ledger localStorage `sf-profile-seen-events` (LRU cap 1000/profil, **JAMAIS cleared** — sinon réconciliation recrée les notifs supprimées). LRU régression-lockée dans `notifications.test.ts` (push 1001 → 1er évincé).
  - `shownToastEventKeys: Set<EventKey>` (type branded importé depuis `helpers/event-bus`) dans le state Alpine est la dédup tab-locale du toast UI. Un même eventKey produit max 1 toast UI par onglet.
  - Combinés : payload 200 + event SSE `completed` dans le même onglet → 1 toast et 1 notif persistée. SSE dans 2 onglets → 2 toasts (UX cohérente où l'user regarde) + 1 notif persistée cross-tabs.
- **Toasts identiques regroupés** (`src/app/toast.ts`, vécu le 2026-10-03 : 18 échecs d'une rafale de quiz empilaient 18 toasts « Réessayer », jamais fermés, sur tout l'écran d'un téléphone) : après la dédup par `eventKey` (inchangée, la cloche garde une entrée par événement), un toast de même `type` ET même `message` déjà affiché n'est pas dupliqué → `count++` (badge `×N` + texte `sr-only`), dernier `retryFn`/`action` non nuls gardés (« Réessayer » relance UNE fois puis ferme le groupe), échéance repoussée. Fermeture automatique par **échéance** (`expiresAt`, null = persistant : erreur + réessai) relue par le minuteur, jamais par un `setTimeout` qui ferme un id : `resetSession` remet `toastCounter` à 0 et un vieux minuteur fermait un nouveau toast au même id. Échec d'une génération simple nommé par son type (`toast.typedError`, « Quiz : … ») : deux types en échec restent deux toasts, chacun avec son réessai. Signature de `showToast` : types de paramètres en alias (`ToastRetry`, `ToastActionSpec`), sinon Lizard ne mesure que la signature.
- **Notifications i18n-aware** : `PersistedNotification` porte `messageKey` + `params` + `paramKeys` (sous-clés à traduire au render — ex: `{ type: 'gen.summary' }`), traduit via `renderNotificationMessage(t)` au moment du `x-text` dans le panneau cloche. La même notif persistée donne une sortie différente selon la langue UI courante. Champ `message: string` legacy conservé en fallback pour les notifs créées avant le refactor i18n.
- **Watermark conservateur lastSeenAt** : `reconcileStartedAt = new Date().toISOString()` capturé AVANT le fetch snapshot. Cutoff de réconciliation = `Date.parse(lastSeenIso ?? reconcileStartedAt)`. Au 1er load après migration, `lastSeenAt` est absent → cutoff = now → zéro backfill historique (pas de spam de 200 notifs sur un projet existant). Set du watermark se fait avec `reconcileStartedAt` (pas `now` post-backfill) pour ne jamais masquer un event arrivé entre snapshot et ouverture SSE.
- **`resetSession()`** (`src/app/session.ts`) invoqué par `selectProfile`, `selectProject`, `deleteProject`. Stop EventSource SSE, abort tous les `abortControllers` + `abortControllersByGid`, vide `loading{}`, `pendingById`, `toasts[]`, `shownToastEventKeys`, reset `confirmCallback` + `confirmTrigger`. **NE TOUCHE PAS** au ledger `seenEventKeys` ni à la liste `notifications` (mémoire persistante du profil, replay au retour). Régression-lockée par les tests négatifs `src/app/session.test.ts`.
- **Validations early extraites des generators** (`routes/generate.ts`) : tout `return null + res.status(4xx)` doit être SORTI en pre-handler AVANT `addPendingEntry`. Sinon un input invalide laisse un pending tracker entry orphelin. Helper `validateQuizReviewInputs` montre le pattern.
- **`storage` event cross-tab** : `src/main.ts` appelle `installCrossTabSync(globalThis, document)` (cf. `src/app/cross-tab-sync.ts`) qui enregistre le `addEventListener('storage', ...)` et bumpe `state.notificationsVersion` quand `sf-profile-notifications` change dans un autre onglet. Le storage event ne fire pas dans le tab qui écrit, donc combiné avec le bump local sur `appendNotification`, tous les onglets convergent. Le helper externalisé permet le test unitaire avec un `globalThis` stubbé.
- **`sf-lastProjectId` namespacé par profil** : map `sf-profile-last-project: {profileId: projectId}` (cf. `src/app/projects.ts` helpers en arrow). Migration silencieuse one-time au boot de la clé legacy `sf-lastProjectId`. Idempotent.
- **Limite documentée Mistral SDK** : la requête en cours côté serveur n'est PAS interruptible. Le cancel ne stoppe pas la facturation, il signifie "on ignore la réponse quand elle arrive" (via `promoteToGeneration` qui retourne `cancelled` et le handler 409).
- **SSE handler garde 404 + write-after-close protection** : `GET /api/projects/:pid/events` vérifie l'existence du projet AVANT `flushHeaders` (sinon listener `EventEmitter` orphelin sur pid bidon, cap 50 → MaxListenersWarning au bout de quelques typos client). `writeGenerationEvent` wrappe les `res.write` dans try/catch + `res.writableEnded` guard (race entre dispatch event-bus et `req.on('close')` → `ERR_STREAM_WRITE_AFTER_END` propagé au listener crashait le process). `res.on('error', ...)` attaché pour cleanup sur reset TCP brutal.
- **Cancel UI optimiste avec rollback** (`src/app/confirm.ts`) : `cancelPendingByGid` retire `pendingById[gid]` immédiatement (feedback instantané), mais si `POST /cancel` échoue (réseau down / 5xx) le snapshot est restauré + toast `cancelFailed`. Sans rollback, l'user croyait que c'était annulé alors que le backend continuait. `postCancel` retourne `boolean` (true si 200 ou 404 = race acceptée, false sinon). Le toast immédiat ajoute l'eventKey `cancelled` du gid à `shownToastEventKeys` : l'événement SSE du même gid n'affiche pas un second toast identique, mais écrit toujours la notification persistée.
- **`runAutoStep` propage le `errorCode` parsé** dans le tuple retourné (`{kind: 'failed', code}`) — `showAutoResult` priorise un toast actionnable (auth_required → settings, quota_exceeded → wait) sur le `partialGenerated` générique.
- **EventSource cap retries** (`src/app/sse-pendings.ts`) : après `RECONNECT_MAX_RETRIES = 8` échecs consécutifs (typiquement projet supprimé dans un autre tab → 404 répété, ou réseau durablement down), on stop la boucle de reconnect au lieu de marteler en backoff exp ad vitam. `console.warn` à chaque retry pour visibilité debug. Un `selectProject`/refresh ultérieur relance avec compteurs réinitialisés.
- **Bus filet anti-uncaughtException** (`helpers/event-bus.ts`) : `subscribeGeneration` wrappe le handler client dans try/catch + `bus.on('error', ...)` global. Sans ce filet, un throw d'un handler SSE (ex: `JSON.stringify` cyclique sur un payload buggué, write-after-end non capturé) remonte en `uncaughtException` et tue le process.

## Sécurité (SAST local)

- **Source de vérité locale** : Opengrep (fork open-source de Semgrep CE) via `npm run security` → `scripts/check-security.sh`. Configs `p/security-audit` + `p/default` + `p/nodejsscan`, `--severity=ERROR --error` (exit 1 sur toute error).
- **Intégration** : `.husky/pre-push` — bloque tout push avec finding ERROR. Pas dans pretest (scan ~12s, trop lent pour boucle commit).
- **Install** : `./scripts/install-opengrep.sh` (binaire standalone ~40Mo dans `~/.local/bin/`, auto-detect linux/osx x86/arm). Pas de devDependency npm (placeholder vide sur registry).
- **Procédure finding SAST avant fix** : (1) identifier le moteur réel et le rule-id exact dans l'annotation (CodeQL, Opengrep/Semgrep via Codacy, SonarQube, ESLint plugin, etc.) ; (2) lire la doc officielle courante de ce moteur/règle ; (3) reproduire localement quand possible (`npm run security`, `npm run lint`, `npm run lint:complexity`, test ciblé) ; (4) chercher les patterns existants dans le repo (`rg "<rule-id>|allowedUrls|nosemgrep|codeql\\[|NOSONAR"`), puis seulement coder. Toujours préférer un fix structurel compréhensible par l'outil à une suppression.
- **Suppression faux positifs** : deux mécanismes
  - Inline : `// nosemgrep: <rule-id> -- <raison>` (ou `// nosemgrep` seul pour ignore générique ligne suivante) immédiatement au-dessus de la ligne flaggée. Sur la MÊME ligne : `<code>; // nosemgrep: <rule-id>`. Multiples rules séparées par virgule.
  - Global : `--exclude-rule=<rule-id>` dans `scripts/check-security.sh` avec commentaire expliquant le pattern récurrent
- **Codacy / Opengrep / Semgrep** : quand l'annotation Codacy indique une source Opengrep/Semgrep, utiliser la doc Semgrep/Opengrep pour la syntaxe. **La syntaxe `// codacy:ignore-next-line` n'existe PAS** — c'est une invention LLM fréquente. Pour ignorer inline côté Opengrep/Semgrep, utiliser `// nosemgrep` ou `// nosemgrep: <rule-id>`. Attention : les rule-ids peuvent être namespacés côté Codacy (ex: `Semgrep_rules_lgpl_javascript_ssrf_rule-node-ssrf`) et ne sont pas toujours présents dans nos packs locaux ; si le ciblage exact est incertain, préférer un fix structurel ou, en dernier recours seulement, `// nosemgrep` seul avec justification.
- **Règle** : avant d'ajouter un ignore (inline ou global), **mesurer** en lançant le scan local pertinent — ne jamais ignorer à l'aveugle un finding Codacy/SonarQube/CodeQL sans avoir identifié le moteur et reproduit quand c'est possible (principe "Mesurer > deviner" ci-dessous). Note : certaines règles utilisées par les services SaaS ne sont PAS dans nos packs locaux ; dans ce cas, le seul moyen de valider le fix est le rescan post-push, donc minimiser les hypothèses et garder le patch structurel.
- **Fix `rule-node-ssrf` préféré = pattern whitelist.includes canonique** (pas d'ignore). Construire `allowedUrls`, puis faire englober directement le `fetch(url, ...)` par un bloc positif `if (allowedUrls.includes(url)) { ... }`. Les early-returns négatifs ou helpers trop éloignés peuvent être fonctionnellement équivalents mais rester invisibles pour l'analyse taint. **Variante URL libre (scraper user-provided)** : quand l'URL n'est pas dans une liste finie, construire une allowlist d'un élément à partir de l'URL déjà validée/canonisée (`buildFetchAllowlist(safeUrlStr) = [safeUrlStr]`), puis `if (allowedUrls.includes(safeUrlStr))` englobe directement le `fetch`. Cette variante est une barrière taint pour scanner, **pas** une validation SSRF autonome : ne jamais la copier sans validation upstream stricte (protocoles, hostnames, IPs privées/réservées, DNS, redirects). Toujours chercher un pattern existant dans le repo avant d'en inventer un nouveau (`rg "allowedUrls|rule-node-ssrf|nosemgrep|codeql\\["`).
- **Suppressions multi-outils** : ne jamais supposer qu'un commentaire vaut pour plusieurs moteurs. CodeQL utilise `// codeql[<query-id>]` sur une ligne de commentaire seule avant l'alerte ; Opengrep/Semgrep utilise `// nosemgrep` ou `// nosemgrep: <rule-id>` ; SonarQube utilise `NOSONAR`. Ne pas combiner deux syntaxes sur le même commentaire : placer des commentaires séparés, chacun au format exact de son outil, avec la justification dans un commentaire lisible au-dessus. Si Codacy affiche un rule-id `Semgrep_rules_... | Source Opengrep`, traiter le finding comme Opengrep même si l'UI mentionne aussi une catégorie générique.
- **Audit SSRF — pièges souvent oubliés** : (1) **RFC 2544 benchmark range `198.18.0.0/15`** (à ajouter aux private ranges avec 0.0/8, 10.0/8, 127.0/8, 169.254/16, 172.16/12, 192.0/24, 192.88/24, 192.168/16, 100.64/10) — un attaquant peut router via cette plage sur certains réseaux internes. (2) **IPv4-mapped IPv6 en format hex** : `::ffff:7f00:0001` est sémantiquement `127.0.0.1` mais le suffix `7f00:0001` ne parse PAS comme IPv4 littéral. Si `isPrivateIPv6` ne reconnaît que la forme textuelle `::ffff:127.0.0.1`, l'attaque hex passe. Fix : tenter `parseMappedIPv4Hex(suffix)` après échec `isIPv4(suffix)`, puis **fail-closed** (`return true`) si ni l'un ni l'autre ne parse — jamais `return false` par défaut sur un suffix `::ffff:` ambigu.
- **Effet secondaire subtil cleanup de dead code** : retirer un export ou un helper apparemment inutilisé peut faire ré-évaluer le graphe de taint par Codacy/Opengrep et **réactiver des findings dormants**. Quand un finding SAST apparaît après un commit "inoffensif", vérifier si la surface d'exports ou le shape du data-flow d'un fichier impliqué a changé.
- **Bump de sécurité ≠ faille corrigée** : une alerte Dependabot passe en `fixed` dès que la version change, même quand l'advisory exige aussi une option. **Lire la section _Patches/Workarounds_ de chaque advisory avant de merger.** Cas vécu : multer GHSA-535w-7cp7-47q4 (DoS CPU, ~2 min de process bloqué par requête) n'est corrigé qu'avec `limits.fieldArrayIndexLimit`, opt-in → **tout `multer({ limits })` DOIT étaler `...MULTIPART_FIELD_LIMITS`** (`helpers/multipart-limits.ts`). Quand un patch de la même majeure corrige la faille, le préférer au saut de majeure proposé par Dependabot et faire la migration dans une PR dédiée (cas vitest 4 → 5 : `npm ci` cassé par le peer `@vitest/coverage-v8` resté en 4.x). **Advisory sans version corrigée** (`first_patched_version` nul : `gh api /advisories/<GHSA>`) : sortir de la chaîne en montant le parent qui ne l'utilise plus, puis vérifier que `npm ls <paquet>` est vide (cas braces ≤ 3.0.3, GHSA-vfj7-8cjw-p6xm, 2026-10 : knip 6.39 a remplacé fast-glob → micromatch → braces par tinyglobby ; ce bump a aussi fait apparaître deux réexportations de type inutilisées que knip 6.4 ne voyait pas).

## Mesurer > deviner (règle OBLIGATOIRE)

**Dès qu'un fait est mesurable factuellement, mesurer AVANT de raisonner dessus.** Ne jamais estimer/supposer quand une vérification coûte quelques secondes. L'intuition est souvent fausse et les itérations basées sur elle coûtent 10× plus cher que la mesure directe.

Cas concrets (non exhaustif) :
- **Calcul** (somme, produit, pourcentage, unités, dates) : bash/python/calculette, jamais à la tête
- **Comptage** : `wc -l`, `grep -c`, `.length`, jamais "à peu près N"
- **Contenu fichier / comportement code** : lire le fichier, `grep`, lancer le test, jamais depuis la mémoire
- **Outils externes** (Codacy CCN, SonarQube, CI warnings) : lancer l'outil localement (`pipx run lizard`, `sonar-scanner`, etc.) pour voir ce qu'il voit réellement, jamais deviner la cause d'un flag
- **Dates relatives** (utilisateur dit "jeudi", "le mois dernier") : convertir en absolu via le contexte date, jamais extrapoler mentalement
- **Syntaxe/annotation d'un outil tiers** (CodeQL, SonarQube, Codacy, Semgrep, ESLint plugin externe…) : **toujours vérifier la syntaxe dans la doc officielle EN COURS** (WebSearch / context7 / docs de l'outil) **AVANT** de pousser une annotation. Mémoire LLM = syntaxes anciennes ou mélangées entre outils. Coût d'une recherche doc = quelques secondes, coût d'une mauvaise annotation = au moins un round-trip CI complet.

**Anti-patterns documentés** :
- Itérer plusieurs commits sur un signal Lizard/SAST sans reproduire localement ni lire la sortie exacte. Les parseurs SAST/complexité ont parfois des quirks (ex: fonctions top-level consécutives agglomérées, data-flow modifié par une extraction). Mesurer d'abord, puis changer le minimum.
- Tenter une suppression SSRF avant de savoir si le finding vient de CodeQL, Opengrep/Semgrep, SonarQube ou d'une combinaison. Les syntaxes se ressemblent mais ne sont pas interchangeables ; lire la doc du moteur exact, chercher les patterns locaux, préférer un fix structurel reconnu (`allowedUrls.includes(...)`) et vérifier les checks PR réels.
- Faire confiance à un garde-fou qui répond « OK » sans l'avoir vu attraper le cas : `check-models` affichait « 7 alias OK » alors qu'OCR 4.1 était sorti et qu'un alias surveillé avait disparu. Tout détecteur doit avoir un test d'acceptation sur l'instantané RÉEL du cas qu'il doit signaler.
- Changer de modèle sur la foi de sa fiche : un modèle plus récent au même prix peut régresser sur NOS données (OCR 4.1 perd des légendes proches des figures). Go/no-go écrit AVANT la mesure, jugement contre la vérité terrain (la photo), plusieurs passages pour la stabilité.

Garde-fou local actuel : `npm test` déclenche `pretest` → enchaîne **`typecheck` + `lint:complexity` + `lint:ci` + `lint:deadcode`** (sortie pipeline en cas d'échec d'un seul). `lint:complexity` → `scripts/check-complexity.sh` (Lizard CCN 8 strict, scope **full-repo `-l typescript`** — toute régression bloque `npm test`). Pièges connus :
- **`-l javascript` ne parse pas les `.ts` en walk-dossier** — Lizard doit être invoqué avec `-l typescript` explicitement, sinon 0 violation silencieusement.
- **`??=` pèse 2 dans le comptage Lizard** (nullish check + assignment) — à retenir lors de l'application du fix `prefer-nullish-coalescing`.
- **`function foo()` top-level consécutives agglomérées** — le parseur Lizard TS peut agglomérer des `function` déclarations consécutives en une seule fonction pour compter le CCN. Fix standard : convertir un des helpers adjacents en `const foo = (): T => { ... }` arrow — Lizard ne les agglomère pas. `export function` délimite aussi correctement. À retenir quand on ajoute un helper privé à côté d'un existant.
- **Type de retour union multi-lignes = corps non mesuré** — Lizard tronque une fonction dont le type de retour est une union écrite sur plusieurs lignes : seule la signature est mesurée (vécu : `buildGenContext`, CCN réel ≈ 15 affiché 1 ; corrigé par alias `GenContextResult` + découpage en `loadGenProject`/`resolveConsigne`/`contextErrorFor`/`assembleGenContext`). Fix : alias de type pour le retour, et découper si le vrai CCN dépasse 8.
- **Paramètre de type fonction écrit en ligne = fonction coupée** — `fn: (ctx: X) => Promise<Y>` dans une signature fait perdre le corps à Lizard (vécu : `runGeneratorAndPersist` absente, `handleGeneration` réduite à sa flèche interne). Fix : alias (`type GeneratorFn = …`, avec le `eslint-disable-line no-unused-vars…` Codacy du fichier).
- **Flèche à corps-expression sur plusieurs lignes** (`=>` en fin de ligne, ou chaîne de `&&` qui continue) : Lizard ne compte que la première ligne (vécu : `allChecksPass`, CCN réel 9 affiché 1 → réécrit en `BODY_CHECKS.every(...)`). Mettre le corps entre accolades dès qu'il porte des branches. Un `??` dans un template literal n'est pas compté non plus.
- **Génériques explicites** — Lizard ne mesure pas une déclaration `function f<T>(…)` (`safeParseJson`, `unwrapJsonArray` absents de la sortie), et un appel générique dont l'argument est lui-même un appel (`unwrapJsonArray<Flashcard>(safeParseJson(raw))`) coupe la fonction appelante à cette ligne (vécu : tout le retry de `generateFlashcards`, `generateQuizWithRetry`… échappait au plafond). Fix : fléchée `const f = <T>(…) => {…}` pour une déclaration, annotation de la variable (`const data: Flashcard[] = unwrapJsonArray(…)`) pour un appel.
- **Paramètre par défaut contenant un appel = fonction invisible** — Lizard (`-l typescript`) ne mesure pas une fonction dont un paramètre par défaut contient un appel (`legacy = new Map()`) : elle échappe au plafond CCN 8 sans signal. Fix : constante de module (`const NO_LEGACY = new Map()` puis `legacy = NO_LEGACY`, cf. `scripts/check-models.ts`), et vérifier que la fonction apparaît dans la sortie Lizard.
- **Expression parenthésée qui commence par un appel = fonction coupée** — `const run = (tails.get(key) ?? d).then(…)` ou `const r = (f(x) + 1) * 2` : Lizard arrête la fonction englobante à cette ligne, le reste du corps n'est pas mesuré (vécu : `withKeyedLock`, 2 lignes mesurées sur 15). Sans appel dans la parenthèse (`(a ?? b).then(…)`, `(x + 1).toFixed()`), rien n'est coupé. Fix : variable intermédiaire (`const previous = tails.get(key) ?? d;` puis `previous.then(…)`), et vérifier la plage mesurée. Cas fréquent au front : `(await res.json()) as T` (vécu : `selectProject`, `refreshConsigne`, `reconcilePendings`) → `const body: unknown = await res.json();` puis `body as T`.
- **Accent grave dans une regex littérale = suite du fichier invisible** — `` /`([^`]+)`/g `` : Lizard y voit l'ouverture d'un gabarit et ne mesure plus aucune fonction jusqu'à la fin du fichier (vécu : `src/app/helpers.ts`, 57 fonctions mesurées sur 128, dont `reconcilePendings`). Fix : `\x60` dans la regex. Contrôle : la dernière fonction mesurée doit se trouver près de la fin du fichier. **Même piège avec `"` et `'`** (vécu : `src/a11y-templates.test.ts`, `/x-text="([^"]+)"/g` → un `it` mesuré sur 59 lignes, que Codacy remonte en « Method has 59 lines of code (limit is 50) ») : `\x22` / `\x27` dans la regex.
- **Appel optionnel `f?.()` = méthodes suivantes invisibles** — après un `this.x?.()`, Lizard peut cesser de reconnaître les méthodes suivantes d'un objet (fabrique `createConfig`, mixin `step-by-step`) ou couper la fonction : leur code est compté dans la fonction englobante, ou pas du tout (vécu : `src/app/config.ts`, `createConfig` arrêtée à la ligne 114 et 14 fonctions mesurées sur 26 ; `handleCrossTabStorageEvent` et `startEditProfile` affichées à CCN 4 et 7 pour un CCN réel de 9). Fix : un `if` explicite (`if (this.x) this.x();`), ou une petite fonction qui porte la seule branche quand le CCN est serré (`reloadMistralVoices`, `src/app/config.ts`), puis vérifier la plage mesurée. Pas `this.x?.call(this)` : Sonar le remonte en S6676 « Unnecessary .call() » (vécu sur #83, 9 issues). Tous les `?.(` ne coupent pas (`routes/generate.ts`, `quiz-vocal.ts` : mesures identiques avec et sans) : contrôler la sortie de Lizard après en avoir ajouté un.

## Design Context

- **`PRODUCT.md`** (racine) : contexte strategique design — registre **produit**, plateforme web, personnalite « ludique, magique, encourageant », positionnement « une photo de lecon → kit de revision complet », cible **WCAG AA**. 5 principes : l'enfant d'abord (les concepts d'adulte — couts, cle API — ne dominent jamais la hierarchie) ; la magie sans le jargon (jamais `MISTRAL_API_KEY` ni « console » dans un texte lisible par l'enfant) ; encourager, jamais culpabiliser ; identite a soi (s'emanciper du decalque Duolingo vers l'univers du logo bleu→violet) ; accessible par defaut.

Regles cles pour toute modif UI : couleurs UNIQUEMENT via les tokens `--color-*` de `theme.css` (jamais de classes Tailwind brutes type `bg-gray-100` — elles cassent le dark mode) ; degrade signature bleu→violet reserve au wordmark/titres de vues/CTA « Auto » ; texte sur aplat vif via la variante `-dark` du hue (AA) ; radii et ombres depuis l'echelle tokenisee, pas de valeur ad hoc.
